## 🤖 Autonomous mode (Fable / великі scoped-таски)

Цей режим **не скасовує** правило вище — він **замінює** мʼяке «питай перед кожною правкою» на «дозвіл наданий наперед на чітко окреслений обсяг, ревʼю по фінальному diff». Вмикається **тільки** коли користувач явно сказав «віддаю це в автономний режим / Fable» **і** дав spec.

**Умови входу (всі обовʼязкові):**
- Є явна команда на автономний прогін + посилання на затверджений `spec`/`plan`/`ADR` у `docs/`.
- Визначений **scope**: які файли/таблиці можна чіпати, що — ні.
- Визначені **acceptance criteria** (що означає «готово»).

**Огорожа (всередині неї — свобода без покрокового підтвердження):**
- Працювати **тільки в окремій git-гілці або worktree**, ніколи не в main/робочій гілці напряму.
- Не виходити за межі `scope`. Якщо завдання вимагає вийти — **зупинитись і спитати**, не розширювати самовільно.
- Перед статусом «готово»: код **збирається**, тести проходять, і підготовлено **повний diff** + короткий звіт змін для ревʼю.
- Нові архітектурні рішення всередині прогону → фіксувати як ADR/amendment і **позначити в звіті** (рішення все одно потребує підпису користувача пост-фактум).

**⛔ Жорсткі інваріанти — діють ЗАВЖДИ, автономний режим їх НЕ послаблює:**
- Усі ⛔-заборони з розділів «База даних» і «Xcode» нижче (не читати/ламати `sourcebible.db` у Linux-sandbox, не запускати `.recover` на робочій базі, тощо).
- Swift 6 strict concurrency + iOS 26 research перед UI-кодом.
- Python скрипти — мінімум 3.10 (див. розділ про Python нижче; правило «під 3.9» скасовано).
- Build має проходити; не лишати код у стані, що не компілюється.
- **Жодних незворотних дій** (видалення/перезапис бази, force-push, зміна схеми user-data без міграції) без окремого явного дозволу — навіть в автономному режимі.

**Вихід з режиму:** автономний прогін завершується видачею diff на ревʼю. Merge у робочу гілку робить користувач (або агент — лише після явного «мерджимо»).

## 📝 Кінець сесії — зібрати рішення на підпис

**Наприкінці будь-якої сесії, що змінила файли або ухвалила рішення, агент подає
короткий список «що ми вирішили» і питає, що з цього йде в `docs/LOG.md`.**

Порядок:
1. **Збирати мовчки по ходу.** Не переривати роботу після кожного рішення — це рве
   потік і перетворює сесію на бюрократію. Тримати перелік у голові до кінця.
2. **Подати одним блоком у кінці**: 1–5 рядків, кожен — уже готове формулювання «чому»,
   не «що змінилось».
3. **Підпис за користувачем.** Він каже «так/ні/переформулюй». Агент не пише в LOG
   самовільно.

Фільтр «що варте рядка» — у `docs/WIKI.md`, розділ «Що варте рядка в LOG». Коротко:
**чи зробить майбутній агент неправильно, не знаючи цього?** Ремонт і полірування — ні.
Відкинута альтернатива, обмеження на майбутнє, куплений виміром урок — так.

Це правило покриває найтоншу діру: рішення, ухвалене в чаті й реалізоване без окремого
документа. Ні git, ні `lint_docs.py` його не бачать. Решту ловлять трейлери `Decision:`
у комітах (`scripts/harvest_log.py`).

## 📋 Docs & знання проекту

### При ініціалізації кожного чату
**Завжди читай `docs/INDEX.md` першим.** Там однорядкові summary всіх ADR, spec і product decision файлів.  
Не читай всі docs підряд — завантажуй конкретний файл тільки коли задача до нього відноситься.

### Коли завантажувати повний документ
- Задача торкається архітектурного рішення → читай відповідний ADR з `docs/architecture/`
- Задача торкається фічі в розробці → читай відповідний spec з `docs/features/`
- Задача суперечить відомому рішенню → читай той документ і поясни конфлікт перед тим як діяти

### Структура `docs/`
```
docs/
├── INDEX.md                  ← читати завжди при старті
├── architecture/             ← ADR файли (Architecture Decision Records)
├── features/                 ← spec і implementation plan для кожної фічі
├── product decisions/        ← PDR файли (Product Decision Records)
└── *.md                      ← reference документація (db_build, system designs)
```

### Правила для нових документів
- **Новий ADR** → `docs/architecture/ADR-NNN-короткий-опис.md` (NNN = наступний номер)
- **Новий spec або plan** → `docs/features/spec-назва-фічі.md` або `plan-назва-фічі.md`
- **Product decision** → `docs/product decisions/PDR-назва.md`
- Після створення документа **завжди додавай рядок в `docs/INDEX.md`**
- Не зберігай spec/ADR/plan поза `docs/` — єдине місце для проектної документації

### Конфлікти рішень
Якщо нова задача суперечить прийнятому ADR або spec — **не виконуй мовчки**.  
Назви конфлікт явно, поясни що змінилось, і запропонуй або оновити документ, або змінити підхід.

## 🔍 iOS 26 API — обов'язковий research перед реалізацією

**Перед тим як писати будь-який UI код для iOS 26 — спочатку research, потім код.**

Це правило введено після того як неправильне використання `HStack` + `ToolbarItem` замість `ToolbarItemGroup` призвело до годин боротьби з розмірами та відступами кнопок — тоді як правильний API вирішив проблему одним рядком.

### Обов'язковий порядок
1. **Search first.** Використовуй WebSearch щоб знайти правильний iOS 26 API для задачі. Запитуй конкретно: назву компонента, відомі проблеми, офіційні приклади.
2. **Перевір документацію.** Зайди на `developer.apple.com` або `createwithswift.com`, `swiftwithmajid.com` — там є актуальні приклади для iOS 26.
3. **Тільки після цього — пиши код.** Не гадай як має працювати API — перевір.

### Конкретні уроки
- **Button groups у toolbar** → використовуй `ToolbarItemGroup`, НЕ `HStack` всередині `ToolbarItem`. `ToolbarItemGroup` автоматично застосовує glass capsule, правильні відступи і розміри.
- **Liquid Glass** → не додавай `.background(.thinMaterial)` або `.glassEffect()` вручну до toolbar кнопок — iOS 26 застосовує glass автоматично через правильний placement і grouping.
- **Corner radius** → ⛔ не встановлюй `.presentationCornerRadius()` або `.cornerRadius()` / `.clipShape(.rect(cornerRadius:))` якщо це не запитано явно. iOS 26 застосовує правильний радіус автоматично (floating sheets — радіус екрана пристрою, кнопки — system capsule тощо). Хардкодний радіус руйнує системну консистентність.
- **HIG / iOS 26 UI Kit** → завжди використовуй стандартні системні компоненти та стилі: `.buttonStyle(.borderedProminent)` + `.controlSize(.large)` для primary actions, `List` зі стандартними row styles для налаштувань, нативні `Toggle`, `Label`, `Form` тощо. Не винаходь власні компоненти якщо є системний еквівалент — він автоматично отримує Liquid Glass, Dynamic Type, accessibility і правильні відступи за HIG.
- Якщо щось не виглядає правильно після першої спроби — **це сигнал що використовується неправильний API**, а не що потрібно більше хаків з padding/frame.

## 🎯 iOS deployment target — обов'язкове правило

**Мінімальна версія: iOS 18. Flip зроблено — `IPHONEOS_DEPLOYMENT_TARGET = 18.0`
в обох конфігураціях `project.pbxproj`** (заміряно 2026-08-07; гілка `ios18-target-flip`,
2026-07-31). Заявлений мінімум і фактичний збігаються.

**Тому:** не пиши iOS 26-exclusive API без `#available(iOS 26, *)` guard і iOS 18 fallback.
Це вже не «на майбутнє» — на 18.0 такий виклик не скомпілюється.

```swift
// ✅ Правильно
if #available(iOS 26, *) {
    // iOS 26 enhanced experience
} else {
    // iOS 18 fallback
}

// ❌ Неправильно — вільне використання iOS 26-only API без guard
someIOS26OnlyAPI()
```

Раніше відомі iOS 26-only діри — **закрито** (compiler-oracle аудит 2026-07-06, Phase A, target=18.0 → 0 unguarded викликів, див. `docs/features/plan-ios18-compat.md`):
- `TabView` value-based tab selection — ✅ покрито iOS 18 split у `ContentView.swift` (legacy fallback); компілятор на 18.0 підтвердив.
- `LocalizedBundle` — це SDK-concurrency (`Bundle` `@MainActor` в iOS 26 SDK), **не** runtime-availability; вирішено через `nonisolated`. Зниження target його не чіпає.

Стан: під target=18.0 кодова база компілюється чисто (Debug+Release+Archive), рантайм-запуск
на iOS 18.0 sim ОК, рідер візуально цілий. **Відкрите — не flip, а QA:** Study Mode / paging /
Menu на iOS 18, SE-валідація, Archive, SPM min-target (`plan-ios18-compat.md`, Phase B).

Entry-умову Phase B «фічі заморожені» свідомо порушено (рішення Івана 2026-07-31): target 26.4
блокував УСТАНОВКУ TestFlight-білда на iOS 18, тож решта фіч у білді коштувала для цих тестерів нуль.

Swift 6 strict concurrency — це налаштування компілятора, не залежить від deployment target. Залишається без змін.

## ⚡ Swift 6 / iOS 26 SDK — обов'язкові правила

Проект компілюється з **Swift 6 strict concurrency** під iOS 26 SDK. Ці правила усувають цілі класи помилок.

### Bundle subclasses
**Bundle отримав `@MainActor` в iOS 26 SDK.** Будь-який `Bundle` subclass успадковує `@MainActor`.
→ Всі overrides + static methods, що мають бути доступні з non-main-actor контексту, **обов'язково** маркувати `nonisolated`.
→ Мutaбельний стан виносити у **file-private globals** з `nonisolated(unsafe) var`, НЕ як `static var` на класі (статичні члени класу успадковують `@MainActor` inference).
→ `let` константи Sendable-типів (`NSLock`, etc.) у тому ж файлі — потребують `nonisolated`,
**БЕЗ** `(unsafe)`: сам `nonisolated` розриває `@MainActor`-inference, а `(unsafe)` на Sendable
`let` нічого не додає, і компілятор позначає її як зайву (`'nonisolated(unsafe)' is unnecessary
for a constant with 'Sendable' type…`). Без жодної анотації — error. Заміряно 2026-08-26 на
двох незалежних близнюкових кейсах: `LocalizedBundle.swift` (`_lbLock: NSLock`) і
`SessionTracker.noop` (`static let` типу `@unchecked Sendable`) — в обох `nonisolated let`
компілюється чисто, без жодного warning; підтверджено повним білдом проєкту 2026-08-31.

```swift
// ✅ Правильно
private nonisolated let _lock = NSLock()           // let Sendable — nonisolated, БЕЗ (unsafe)
// swiftlint:disable:next nonisolated_unsafe
private nonisolated(unsafe) var _state: String = ""

final class MyBundle: Bundle, @unchecked Sendable {
    nonisolated override func localizedString(...) -> String { ... }
    nonisolated static func activate(...) { ... }
}

// ❌ Неправильно — static var на класі → @MainActor inference cascade
final class MyBundle: Bundle {
    private static var _state = ""   // ← заразить весь клас
}

// ❌ Неправильно — let зовсім без nonisolated у файлі з Bundle subclass
// "Main actor-isolated let cannot be referenced from nonisolated context"
private let _lock = NSLock()

// ⚠️ Компілюється, але зайве — компілятор сам пропонує прибрати `(unsafe)`
private nonisolated(unsafe) let _lock = NSLock()
```

### Closures з @escaping та instance methods
**Swift 6:** виклик instance method всередині `@escaping` closure вимагає явного `self.`.
→ Якщо метод не використовує `self` state → **винести у file-level func**. Це чистіше і не потребує `self.` capture.

```swift
// ✅ Правильно — file-level func, no self capture needed
private func nowMs() -> Int64 { Int64(Date().timeIntervalSince1970 * 1000) }

// ❌ Неправильно — instance method в @escaping closure без self.
class Store {
    func nowMs() -> Int64 { ... }
    func write() { db.write { nowMs() } }  // ← Swift 6 error
}
```

### Visibility та private types
**Swift 6:** property не може бути більш видима, ніж її тип.
→ Якщо клас або struct є `private` — всі properties теж `private`.
→ Якщо property посилається на `private` тип → або зробити property/клас `private`/`fileprivate`, або використати протокол як тип (`(any UITextViewDelegate)?` замість `PrivateCoordinator?`).

### UIViewControllerRepresentable для клавіатури в sheets
**Замість `UIViewRepresentable` + `DispatchQueue.asyncAfter` для `becomeFirstResponder()`.**
→ Завжди використовувати `UIViewControllerRepresentable` + `viewDidAppear()` — гарантований момент після sheet-анімації.

## 🔬 Дані перед висновком — обов'язково

**Не роби висновків і не пропонуй рішень із пам'яті чи припущень. Спочатку подивись у реальні дані.**

Правило введено 2026-08-04 після ремонту транслітерацій. Ланцюжок неперевірених припущень коштував кількох ітерацій, а одне з них **змінило напрям роботи**: твердження «BSB має іншу нотацію» походило з колонки старого звіту, яка читала не те поле. Сирий `bsb_tables.tsv` дає ту саму школу, що й BibleHub.

### Обов'язковий порядок
1. **Виміряй, потім називай.** «Приблизно сотня» і «1 427» ведуть до різних рішень. Обсяг роботи — половина архітектурного рішення; оцінка на око закладає помилку у фундамент.
2. **Прочитай, а не згадай.** Назва колонки, тип повернення функції, формат посилання — відкрий файл. Пам'ять про версифікацію так само ненадійна, як пам'ять про API.
3. **Познач неперевірене вголос.** Якщо щось лишилось припущенням — воно має бути назване припущенням у тексті рішення І мати охоронця в коді.

### Конкретні уроки 2026-08-04
- **Не стверджуй про версифікацію з пам'яті.** «У Бутті розходжень немає» — хибно: Бут. 32 (євр. 32:1 = англ. 31:55), 30 зіпсованих віршів.
- **Еталон теж може бути хибним.** Два з сімнадцяти якорів (Лев. 6:1, Еккл. 5:1) були записані перевернутими — скрипт «падав» на власній правильній поведінці. Провал перевірки має друкувати очікуване поруч з отриманим, щоб було видно, хто саме помиляється.
- **Не припускай форму даних чужої функції.** `parse_hebrew_translit()` повертає кортежі `(surface, translit, strong)`, а не словники. Припущення пережило три раунди «протестовано» і впало на першому живому вірші.
- **Різні джерела членують текст по-різному.** Довжини слів BSB не збігаються з BibleHub (4 сторінки з 4 970, і мовчазний зсув межі на спільних сторінках). Не переноси лічильники з одного джерела на інше — перераховуй по тому, яке ріжеш.

## 🌍 Локалізація — swizzle підміняє БАНДЛ, а не `Locale.current`

**Заміряно 2026-08-17 (bug-041), не виведено з документації.** `LocalizedBundle` (ADR-006)
підміняє бандл, з якого беруться рядки, тож `NSLocalizedString` слухається мови застосунку.
Але правила МНОЖИНИ й будь-яке локале-залежне форматування беруться з `Locale.current` —
це СИСТЕМНА мова. Обкладинка з plural-варіаціями показала «3 розділу»: українська таблиця
+ англійське правило (3 → `other`).

- ⛔ **Не використовувати `String(localized:)`** — він взагалі НЕ проходить через swizzle.
  `LocalizedBundle` перекриває лише `Bundle.localizedString(forKey:value:table:)`, тому
  `Text("key")` і `NSLocalizedString` слухаються мови застосунку, а `String(localized:)`
  мовчки резолвиться проти СИСТЕМНОЇ локалі. Заміряно 2026-07-13 (кластер bug-005, 018,
  019, 021, 024, 025, 027a): усі 272 uk-рядки були на місці — ламався не переклад, а шлях
  до нього. Симптом підступний: на одному екрані частина рядків локалізується, частина ні.
- ⛔ Не форматувати plural-ключ через `String.localizedStringWithFormat` або `String(format:)`
  без локалі. Тільки `String(format:locale:)` з `\.locale` середовища (його виставляє
  `SourceBibleApp.swift` з `appLanguage`), або `Text("key \(n)")` — той бере локаль сам.
- ⛔ Не збирати «число + іменник» тернаром `count == 1 ? … : …`: це англійське правило,
  українська має три форми (одна нова мова — і воно знову зламане). Кількість → у plural-ключ
  із ПОВНИМ набором категорій uk: one/few/many/other.
- Гейт: `python3 scripts/lint_localization.py` (ненульовий код виходу) — ловить обидва
  антипатерни плюс неповні категорії й мертві ключі з числом.
- Урок ширший за локалізацію: фікс, що компілюється, ще не фікс. Тут правильний за виглядом
  код дав неправильний рядок, і показав це лише **запуск** на симуляторі.

## 🧪 Перевірки — у код, не в очі

**Будь-яка перевірка, яку можна описати словами, має бути написана як код із ненульовим кодом виходу.**

⛔ **Не пропонуй користувачу «поперевіряй очима», grep або ручне порівняння.** Якщо перевірку варто зробити — вона варта того, щоб жити в скрипті й падати сама.

### Що мусить мати кожен скрипт, який пише дані
1. **Еталонні випадки** — відомі правильні відповіді, зашиті в код, плюс контрольні, що НЕ мають спрацьовувати (щоб ловити протилежну помилку).
2. **Структурні інваріанти** — монотонність, відсутність дублів, покриття без дір і накладань. Перевірка черепиці сегментів зловила те, чого перевірка рівня вірша не могла навіть висловити.
3. **Ненульовий код виходу** — оркестратор зупиняється на провалі, а не несе зіпсоване далі.

⛔ **Валідатор, який лише відмовляється писати, лишає стару помилку жити.**
Стадія 5 ремонту відхилила 10 віршів за розбіжністю Strong's — і всі 10 лишились показувати чужу транслітерацію, записану раніше. Відмова мусить **прибрати** наявний хибний запис, якщо той не кращий за відхилений. Порожньо + fallback чесніше, ніж збережена помилка.

### Автотести
- **Тест, який годують вигаданими даними, перевіряє припущення автора, а не код.** Синтетична фікстура мусить відтворювати РЕАЛЬНУ форму: якщо парсер віддає кортежі — тест дає кортежі.
- Тести для скриптів даних живуть у `scripts/tests/`, запускаються без мережі й без бази: `python3 -m unittest discover scripts/tests`.
- Кожен виправлений баг отримує тест, який падав би до виправлення.

## ⛔ ЗАБОРОНИ — не повторювати ці помилки

### База даних

**⛔ НІКОЛИ не писати в `sourcebible.db` з Linux sandbox. Читати — можна, але спершу перевірити.**

Заміряно 2026-08-07: read-only з пісочниці **працює**. Файл більше не sparse — 350 MB фізично проти 342 MB логічних, `sqlite3.connect("file:sourcebible.db?mode=ro", uri=True)` відкривається й віддає дані без помилок.

Попереднє формулювання («не читати взагалі») описувало інший стан файлу: 24 MB фізично / ~149 MB логічно, тобто APFS sparse. Linux читав sparse holes як нулі → SQLite error 11 (SQLITE_CORRUPT), «database disk image is malformed». База з того часу виросла й матеріалізувалась, тож заборона читання втратила підставу — і суперечила кастомним інструкціям проєкту, які кажуть «через міст лише ЧИТАТИ».

Що це означає на практиці:

- **Читання для замірів — ОК** і бажане: без нього рішення приймаються з пам'яті (див. «Дані перед висновком»). Відкривати **тільки** `mode=ro`, ніколи не звичайним `connect()` — той створює `-wal`/`-shm` поруч із базою.
- **Sparse-стан може вернутись.** Свіжа збірка/копіювання через APFS clone знову дасть діри. Тому не вважати читання гарантованим: якщо `sqlite3` віддає SQLITE_CORRUPT (error 11) — це не зламана база, це sparse через міст. Перевірити `ls -ls` (фізичні блоки проти логічного розміру) і перенести заміри на Mac, а не «лагодити» базу.
- **Скрипти, що ПИШУТЬ** (`build_db.py`, `build_versification.py`, `import_commentaries.py`, `process_glosses.py`, будь-яка міграція) — **тільки на Mac** (`~/Projects/SourceBible/`). Запис через міст у sparse-файл — шлях до тихого пошкодження.

**⛔ Не запускати `.recover` на робочій базі.**
`.recover` витягує тільки некорумповані сторінки. Sparse сторінки (де живуть `verse` і `strongs`) не відновлюються → база після `.recover` втрачає ці таблиці. Зламали робочу базу саме так.

**⛔ `build_db.py` не будує `verse_org`.**
Це окремий крок (`scripts/build_versification.py`). Завжди запускати після build_db.py
(канонічно — через `./rebuild.sh`, який також створює `idx_verse_org_rev`).
Без verse_org «Оригінал» і крос-рефи падають в identity-fallback у зсунутих главах.

**⛔ Не брати xlit sub-entry від базового Strong's номера.**
H871a (прийменник בְּ) і H871 (місто Атарот) — абсолютно різні слова. Strip suffix для xlit = неправильний xlit. Fallback H835a→H835 безпечний тільки якщо `original[0]` збігається.

**⛔ При зміні `_parse_stepbible_file()` — перевіряти regex `data_re` для TBESH suffixed IDs.**
Баг виявлено у червні 2026: regex `r'^[HG]\d{4,5}\t'` мовчки скіпає 1 424 рядки TBESH де `eStrong#` = `H1471a`, `H6213a`, `H6743b` тощо. Для ~542 Strong's IDs у TBESH взагалі немає bare-number рядка — тільки suffixed. Результат: `short_def`/`long_def` = NULL для цих слів (наприклад H1471 גּוֹי, H6213 עָשָׂה, H5034 נָבֵל).

Правильний regex: `r'^[HG]\d{4,5}[a-z]?\t'` — дозволяє опціональний суфікс. Плюс треба propagate дані suffixed-row → базовий ID (H1471a → H1471).

Деталі і код виправлення: `docs/db_build.md` → розділ "TBESH suffixed eStrong# entries".

**⛔ Плоский текст вірша для показу — тільки з `verse.text_clean`. Не знімати розмітку в рантаймі.**

ADR-034. Правила зняття `<S>/<f>/<n>/<i>` існували двічі — у `build_db.py::_search_text()`
і в Swift — і роками розходились: 261 вірш просочував СЛОВО з багатономерного тега
(`<S>8147, Joshua82</S>` → «…are like two, Joshua fawns…»), 1 330 показували маркер
виноски `[2]` як текст. Рідер був правильний (він іде через `VerseParser`), биті були
концорданс, крос-рефи, паралельні й сніпет пошуку — тому й не помічали.

- Новій поверхні треба текст вірша → `SELECT text_clean`, а не `text` + strip.
- `verse.text` лишається джерелом для **парсера** (структура, тапи по словах, `<f>` → †).
- `strippingBibleMarkup()` і `DatabaseService.stripBibleMarkup()` видалені. Не відроджувати
  «як зручний хелпер» — саме зручність зробила з них другу реалізацію правил.
- Виняток один: `strippingBibleMarkupKeepingSpaces()` — працює над ФРАГМЕНТАМИ
  (сегментами `VerseParser`), не над віршем, тож колонкою не замінюється.
- Наслідок: зміна правила показу вимагає перезбірки бази, не патча застосунку.

## Схема word table (важливо — не плутати колонки)

```sql
word(id, book_id, chapter, verse, position, surface, lemma,
     strongs_id, morph, gloss, language, xlit,
     gloss_macula,   -- ← не gloss! перейменовано
     syntax_role, greek, greek_strong,
     after_char,     -- trailing char from Macula XML (maqaf ־, sof pasuq ׃)
     lexical_class,  -- Macula TSV `class` field
     slot,           -- Macula !N group position (multiple tokens share same slot = 1 display word)

```
`gloss_macula` — стара назва була `gloss`, перейменована. Якщо код падає з "no such column: w.gloss_macula" — база стара, потрібна перезбірка.

## verse_org — версифікація (ADR-028)

Тотальний курований маппінг «вірш перекладу ⇄ вірш оригіналу» (UBS .vrs + O2-верифікація
через Strong's; розбіжність = білд падає). Обслуговує «Оригінал», крос-рефи і конкорданс.
Крос-глава (RST Псалтир = Heb−1, Дан 3/4, Йона 2), N:M і «немає оригіналу» (org NULL) —
першокласні випадки. Reverse-хоп (оригінал→переклад) використовує `idx_verse_org_rev`
(створюється у `rebuild.sh`, НЕ у замороженому `build_versification.py`).

**⛔ Будь-яка поверхня, що показує вірш ІНШОГО перекладу, ніж відкритий, зобов'язана йти
через `verse_org`.** Номер вірша не є ключем між перекладами з різними схемами. Так впали
паралельні переклади (bug-036, виправлено 2026-08-16): фаза 2 мігрувала трьох споживачів
**старої `verse_map`** — «Оригінал», крос-рефи, конкорданс, — а панель «Переклади»
`verse_map` ніколи не читала, тож у список робіт не потрапила й лишилась на identity:
2 705 хибних рядків RST і 3 367 UBIO при читанні KJV, Псалтир зсунутий на главу в обох.
Правильний шлях — два курованих хопи (`orgRef` → `translationRef`), як у
`DatabaseService.loadParallelVerseTexts`. Гейт: `scripts/verify_parallel_alignment.py`
(у `rebuild.sh`, перед `cp` у бандл).
Відомий залишок того ж класу: закладки (bug-037) — `bookmark_verses` не зберігає переклад,
тож хопати нема від чого; потребує рішення, не просто фіксу.

Очікуваний розмір: **155 621 рядок** (5 перекладів × ~31k). Якщо суттєво менше — щось пішло не так.
Стара евристична `verse_map` (7 292 рядки, 57% хибних) видалена в ADR-028 фазі 2 —
не відроджувати; мапінг НЕ виводити наново евристикою.
