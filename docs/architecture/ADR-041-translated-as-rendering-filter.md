# ADR-041: «Translated as» — як переклад передає слово оригіналу (графік у Meaning + чипи-фільтр у Usage)

**Status:** Proposed (adversarial review 2026-09-28 внесено — див. розділ «Adversarial review»)

**Amendment 2026-09-28 (рішення Івана):** NASB у v1 **пропускаємо** — рядків `word_rendering` для NASB не будуємо, фіча для NASB прихована гейтом п.4(б) (ліцензійне питання не вирішене). Бюджет **~20 МБ прийнято**; без NASB очікувано менше (3 переклади з 4) — точний замір у spec. Решта рішень без змін.

**Amendment 2026-09-28 (2) — UX за результатами експерименту на демо (8 ітерацій з Іваном):** розділ 5 переписано. Фільтр задає **точка входу**. Скасовано сесійні рішення №2 (фільтр у самому Usage-табі) і №7 (фільтр за замовчуванням з вірша + чип All у Usage). **Amendment 2026-09-29 (3) — фразові дієслова (рішення Івана, варіант «зберігати фразу»):** у п.2 кінцеві прислівникові частки (`PARTICLES_EN`: over, through, away, past, by, out, up, down, off, forth, back, about, again, together, near…) лишаються частиною передачі: «passed over» → «pass over», а не «over». Чисті прийменники (in, on, to, into, upon…) частками не є — «trust in» → «trust». Злиття форм (mercies→mercy) змінює останнє НЕ-частка слово; згортання суфікса не зводить фразу до голої частки. Неправильні дієслова (went/go, came/come) і далі не зливаються — відоме обмеження.

## Контекст

### Як дійшли до цього рішення

Іван знайшов референс (Strong's Usage у стороннього застосунку): чипи з англійськими передачами слова оригіналу з лічильниками + список віршів з підсвіткою, і графік «Translated as» під лексичною статтею. Щоб перевірити, чи «гра варта свічок», зібрали демо на реальних даних `sourcebible.db` для חֶסֶד (H2617), 2026-09-26.

Що показало демо на живих даних:

- **Лексикон мовчить там, де переклад говорить.** Уся лексична стаття H2617 у базі — `goodness, kindness, faithfulness`. KJV у 61% входжень (149 з 245) передає слово як **mercy**, якого в статті немає. Графік робить розрив між словником і перекладацькою практикою видимим за секунду — це і є цінність фічі для pro deep-study аудиторії.
- **Переклади видимо розходяться:** KJV — mercy 149 / kindness 39 / lovingkindness 30; ASV — lovingkindness 168 з 237. Це і є урок про слово.
- **Омонім виходить на поверхню.** Лев 20:17 і Прип 14:34 = `H2617a` (חֶסֶד II «ганьба»): KJV «wicked thing», «reproach». Групування конкордансу вже точне (bug-045 + `StrongsMergeMap`, H2617/H2617a не зливаються) — графік мусить використовувати той самий ключ.
- **Прототип, що сканував теги перекладу напряму, був хибний у трьох місцях:** тег `<S>2617</S>` без префікса H/G ловить і G2617 καταισχύνω у НЗ; не розводить омоніми; не знає версифікації (RST Псалми). Звідси рішення №1 нижче.

### Сесійні рішення Івана (фаза 1–2 feature-pipeline, 2026-09-26…28)

1. Обсяг v1: графік у Meaning + чипи у Usage (фікс омонімів уже зроблено в bug-045).
2. Тап по стовпчику/чипу → Usage-таб із фільтром (не окремий sheet).
3. RST лематизується в білді зараз, а не відкладається.
4. Показуємо **лише для перекладу, обраного в читанці**; немає Strong's-розмітки → фіча прихована (без заглушки).
5. Словоформи одного слова зливаються (mercy/mercies, lovingkindness/lovingkindnesses); різні частини мови — ні (kindly, merciful окремо).
6. Фільтр одиночний (не мультивибір).
7. **Фільтр за замовчуванням = передача, актуальна для цього вірша і перекладу.** Чип **All (N)** замість «Clear filter».

## Рішення

### 1. Якір — Macula, не теги перекладу

Ланцюжок: `word` (точний `strongs_id`, ключ групи = канонічний id з `StrongsMergeMap`) → reverse `verse_org` (identity, якщо рядка немає; **1:N** — напр. Пс 13:6 MT → KJV 13:5+13:6 — обробляється як один пул) → вірш(і) перекладу → сегменти → зіставлення.

**Еталон зіставлення — `ReaderViewModel.verseWordSegmentPairs` (ReaderViewModel.swift:381), а не власне правило.** Python-крок портує його дослівно: пул слів Macula за `resolvedMaculaBase` (включно з `nasbExtendedOverride` — NASB тегує חֶסֶד II як `9155`, без оверайду H2617a у NASB зіставляється 0 з 2), сегменти перекладу в порядку читання, consume-in-order, пропуск повторного `word.id` (NASB тегує одне слово двома сегментами: «dealt<S>1580</S> bountifully<S>1580</S>»). Сегментація — як у `VerseParser`, не regex з `highlightedVerseText`. Так графік і клікабельність гарантовано говорять про ті самі пари.

Це автоматично: відсікає інший заповіт (якір — мовна колонка Macula), розводить омоніми, коректно йде через версифікацію RST.

Заміряно на всьому корпусі (2026-09-28, скрипт-прототип): з ~607 тис. слів Macula з Strong's сегмент знайдено для 320–343 тис. (залежно від перекладу); решта — номер відсутній у вірші перекладу (частки, артиклі, `את`, вав — не перекладаються окремим словом). Випадків «номер у вірші є, але k-того сегмента нема» — одиниці тисяч з ~600 тис.

### 2. Нормалізація сегмента → «передача» (build-time, Python)

1. Прибрати службові слова в кінці сегмента; взяти хвіст **після останнього службового слова** («for his mercy» → mercy, «it is a wicked thing» → wicked thing). Список стоп-слів — окремий для EN і RU, в репо.
2. **EN — злиття форм з перевіркою на «сусіда»:** форма зводиться до іншої (−s/−es/−ies/−ed/−eth/−est/−ing), **лише якщо та друга форма теж зустрічається як передача цього ж Strong's** у цьому ж перекладі. Жодного зовнішнього лематизатора для англійської; не вигадує форм, яких немає в даних.
3. **RU (RST) — лематизація `pymorphy3` 2.0.6 + `pymorphy3-dicts-ru` 2.4.417150.4580142** (перевірено: милости/милостью/милостию → милость). Стоп-слова перевіряються **і по лемі** (інакше «его» → «он» проходить як передача). Нормалізація повна й детермінована: зняти розмітку (`<t>`, `<pb/>`, `[..]`, `»`), пунктуацію, NFC, lowercase. Версії пінуються в `requirements-build.txt`.
4. **Згортання суфікса з перевіркою на «сусіда»:** багатослівна передача зводиться до свого найдовшого суфікса, якщо той існує як окрема передача цього Strong's («ye showed kindness» → kindness; «wicked thing» лишається — «thing» як передачі H2617a нема).

Результат для H2617 (заміряно): KJV — 10 передач, шуму нуль; ASV — 7 шумних входжень з 237 (~3%: «man», «vav», «s sake», «concerneth» — зсунуті теги ASV); RST — 244 входження, `милость` 195, хвіст з поодинокими займенниками до виправлення п.3; NASB — ~4% шуму («david», «away», «hast made»).

### 3. Збережені дані — таблиця на входження (Swift не нормалізує нічого)

Перша редакція тримала агрегат + мапу форм і змушувала Swift повторювати нормалізацію. Review показав два блокери: (а) відфільтрований список однаково вимагав розбору всіх віршів слова в рантаймі (אָמַר = 5 307) — тобто відкинутий варіант A; (б) RST-нормалізація залежить від леми (стоп-слово по лемі), якої Swift не має → `form` розходиться. Тому зберігаємо результат **на входження**:

```sql
CREATE TABLE rendering (id INTEGER PRIMARY KEY, lang TEXT NOT NULL, text TEXT NOT NULL, UNIQUE(lang, text));
CREATE TABLE word_rendering (
  translation  TEXT    NOT NULL,
  strongs_key  TEXT    NOT NULL,   -- канонічний id групи StrongsMergeMap
  rendering_id INTEGER NOT NULL,   -- → rendering.id
  verse_key    INTEGER NOT NULL,   -- book_num*1000000 + chapter*1000 + verse (вірш ПЕРЕКЛАДУ)
  seg_ord      INTEGER NOT NULL,   -- порядковий № сегмента з цим номером у вірші (зазвичай 0)
  PRIMARY KEY (translation, strongs_key, rendering_id, verse_key, seg_ord)
) WITHOUT ROWID;
```

- **Графік:** `SELECT rendering_id, COUNT(*) … WHERE translation=? AND strongs_key=? GROUP BY rendering_id` — префікс PK, без окремого індексу.
- **Фільтр:** `… AND rendering_id=? ORDER BY verse_key` → список віршів; підсвітка = сегмент № `seg_ord` у вірші. **Swift не нормалізує і не лематизує** — лише парсить сегменти тим самим `VerseParser`.
- **Розмір:** синтетичний замір на ~1.15 млн рядків (4 переклади) — **~21 МБ** (SQLite зберігає 0/1 без payload, тож `seg_ord` майже безкоштовний). База 383 МБ → +~5%. Точний замір на реальних даних — у spec; якщо бюджет не прийнятний, запасний шлях — зберігати лише переклади, що шипляться (див. NASB).
- **Паритет:** golden-тест тепер перевіряє не нормалізацію, а **сегментацію** (Python-порт `VerseParser` ↔ Swift): ~500 реальних віршів, включно з 1:N `verse_org`, NASB `<t>/<pb/>`, суміжними тегами RST.

### 4. Гейт показу

Фіча (і графік, і чипи) показується, коли **усі три**: (а) поточний переклад читанки має Strong's-розмітку, (б) для цього слова в цьому перекладі є рядки `word_rendering`, (в) **покриття ≥ 0.8** — частка входжень слова, для яких знайдено передачу. Інакше графік показував би σύ G4771 за 6% вживань (KJV: 176 з 2 893; артикль G3588 — 538 з 19 789), бо займенники/артиклі в перекладі часто не тегуються окремим словом. Інакше — нинішній Usage по книгах без змін, графіка немає, заглушки немає. Огієнко (UBIO, 0 тегів) — прихований до `verse_markup` (ADR-016 Phase 2).

### 5. UX (Amendment (2), демо v8: https://claude.ai/artifact/HMS1q252jyKv1KvTAjgLg8)

Каркас Word-табу не змінюється: сегмент Verse / Word, пілюлі Meaning / Usage.

**Meaning — нова секція «Translated as · {переклад}» одразу після лексикону.** Причина розміщення: цінність у контрасті «словник каже goodness, kindness, faithfulness — KJV каже mercy (149/245)», він видно лише поруч. Рядок = передача · смуга · кількість · шеврон `›`. Топ-5 + «Show N more»; рядок передачі з поточного вірша позначено «this verse» (показується навіть поза топ-5). Підпис з одиницями, якщо зіставлено не все: «237 of 245 occurrences in ASV». Тап по рядку → stacked sheet із цією передачею; «All N occurrences ›» → sheet без фільтра. Без підказок на кшталт «Tap a bar…» — афорданс дає шеврон (урок 2026-08-02: рядок без афордансу читався як «застосунок сам кудись поїхав»).

**Usage.** Заголовок «N occurrences in the Bible», далі **по одному прикладу на кожну передачу**: передача · кількість · вірш-приклад із підсвіченою передачею · шеврон → sheet із цією передачею. Внизу кнопка «Show all N occurrences» → sheet без фільтра. Правило вибору вірша-прикладу — відкрите (перший канонічний / поточний вірш / найкоротший), вирішити при реалізації частини 5.

**Stacked sheet «חֶסֶד · Usage».** Шапка: SheetCloseButton, заголовок + підпис перекладу, **пікер книг праворуч** («All books ▾», меню з кількостями). Під шапкою — **чипи передач, що переносяться на кілька рядків** (усі варіанти видно одразу, як у референсі): «All N» першим, далі за спаданням, одиночний вибір; висота блоку обмежена ~40% аркуша з вертикальною прокруткою для слів з довгим хвостом (перевірити на אָמַר). Рядок стану: «Showing X of N · mercy» / «N occurrences · M verses». Список — вірші, згруповані по книгах (sticky-заголовки), підсвічено лише входження вибраної передачі. Кількості в чипах і в пікері книг враховують фільтр одне одного.

**Тап по вірші → читанка на цьому вірші** (підсвітка вірша + підкреслене слово). Навігація **додається в back-stack** (як крос-рефи), не `.fresh`: «‹ Usage» повертає в sheet з тим самим фільтром і прокруткою.

**Фільтр задає точка входу:** рядок таблиці / приклад у Usage → ця передача; «All …» / «Show all» → без фільтра. Окремої логіки «фільтр за замовчуванням з вірша» немає.

**Без розмітки (UBIO) або гейт не пройдено:** секції «Translated as» немає; Usage — нинішній по книгах + «Show all»; у sheet немає чипів передач, список і пікер книг працюють.

## Наслідки

- **+** Нова, помітна цінність для pro-аудиторії без нової ручної курації; працює для KJV/ASV/NASB/RST одразу.
- **+** Узгоджено з Usage: той самий ключ Strong's (`StrongsMergeMap`), ті самі лічильники.
- **−** Новий крок `rebuild.sh` — **після** `build_strongs_merge_map.py` (ключ групи) і **до** `cp` у бандл; перевикористовує функцію групування звідти. Swift отримує `StrongsMergeMap.canonical(_:)`. Нова build-залежність `pymorphy3` у новому `requirements-build.txt`, `rebuild.sh` перевіряє встановлення.
- **−** +~20 МБ до бази (див. п.3).
- **−** Сегментація в двох мовах (Python-порт `VerseParser`) → golden-тест сегментації обов'язковий.
- **−** Шум ASV/NASB ~3–4% для hesed видимий у хвості графіка (поодинокі стовпчики під «Show more»). Прийнятно для v1; окремо — дефект 2 (дрейф тегів ASV) лишається відкритим.
