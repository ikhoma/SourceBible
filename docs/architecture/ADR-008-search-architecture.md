# ADR-008: Search Architecture — MVP

**Status:** Accepted (amended 2026-06-11, 2026-07-07, 2026-08-06, 2026-08-07)  
**Date:** 2026-05-23  
**Deciders:** Ivan

## Context

iOS offline-first Bible app. Потрібен пошук по тексту перекладу. DB — SQLite bundle (read-only, `immutable=1`). Existing: `word` table (Macula, lemma/morph/strongs_id), `verse` table, `strongs` table.

## Decision

**V1 MVP: FTS5 + SQL joins. Без vector search.**

1. `verse_fts` — FTS5 virtual table (`content='verse'`, `tokenize='unicode61 remove_diacritics 2'`). Будується в `build_db.py` один раз.
2. `search_terms` — deduplicated word list з verse text для autocomplete (GLOB prefix scan).
3. `SearchViewModel` — debounce 280ms, `Task.detached` для DB queries off main thread.
4. `SearchView` — `.searchable` (нативний iOS API) + `Tab(role: .search)`. Предіктів і результати рендеряться **inline** в основному `List` (Apple Music pattern). **Без `.searchSuggestions`** — див. amendment 2026-06-11.

**Out of scope (amendment 2026-07-07):** Strong's/lemma/morph пошук у search-барі **виключено** — сценарій "ввести номер стронга в пошук" нереалістичний для цільового користувача. Доступ до Strong's/lemma вже реалізовано природним шляхом: тап по слову → Word page → лексикон/конкорданс (ADR-013, ADR-016). Не реалізовувати.

## Amendment 2026-06-11 — drop `.searchSuggestions`, predictions→results model

**Контекст:** на iOS 26 системний `.searchSuggestions` overlay лягає окремим шаром і стискає `content` у вузьку смугу (зсуви ширини + різний фон у "Searching…"/"Nothing found"). Перша спроба (живі inline-результати під час набору) дала іншу проблему: щільний текст результатів малювався позаду предіктіва й напівпрозорого нижнього бара ("rendering underneath"), а тап по підказці, якої нема в активному перекладі, давав порожній екран.

**Рішення (модель "предіктів → результати"):** прибрати `.searchSuggestions`; розділити дві фази:
- **Набір (uncommitted):** показуємо **тільки** список предіктіва (`predictiveList`) — без результатів під низом. Префікс терміна `.primary`, продовження `.secondary` (Apple Music "**dak**ooka"). Якщо підказок нема — один рядок для пошуку буквального тексту.
- **Коміт** (тап підказки / синій Search / `onSubmit`): `committedQuery` = запит, запускаємо `vm.search`, ховаємо клавіатуру (`resignFirstResponder`), показуємо повноекранну сторінку результатів (`resultsList`); 0 результатів → центрований "Nothing found" (`emptyResultsView`), а не порожнеча.
- Редагування тексту після коміту (`trimmedQuery != committedQuery`) → назад у предіктів. Скасування пошуку (✕) скидає `committedQuery`.

`vm.search` більше **не** викликається на кожне натискання — лише на коміт.

**Не змінюється:** `.searchable` + `Tab(role: .search)` (нижній бар + морф-анімація), FTS5, `search_terms`, `DatabaseService.suggestTerms()`/`searchByText()`, debounce. Зміна суто на рівні презентації UI (`SearchView.swift`).

**Відомий борг (крок B, окремий спринт):** `search_terms` будується з усіх перекладів (`build_db.py` → `build_search_terms`, `SELECT text FROM verse`), а `searchByText` фільтрує по `v.translation`. Тому предіктів може пропонувати слово, якого нема в активному перекладі (напр. "bloodshed" у KJV) → коміт дає "Nothing found". Фікс: зробити `search_terms` по-перекладним (колонка `translation`, `suggestTerms(prefix:translation:)`). Потребує ребілду бази.

## Amendment 2026-07-07 — infinite scroll + YouVersion-style filters (Translation / Testament / Book)

**Контекст:** `searchByText` мав жорсткий `LIMIT 150` — для частих слів користувач бачив довільні 150 результатів без можливості дійти до конкретного вірша. Фільтр Testament був клієнтським (фільтрував уже обрізаний список), segmented control All/OT/NT — замалий для розширення.

**Рішення:**

1. **Пагінація в SQL (infinite scroll).** `searchByText` отримав `limit`/`offset` (сторінка = 50) + `bookIds: [String]?` фільтр (`AND v.book_id IN (…)`). `ORDER BY rank, verse_fts.rowid` — rowid-tiebreak робить LIMIT/OFFSET детермінованим при рівних BM25 rank. Нові методи: `searchResultCount()` (COUNT для хедера, без кепа) і `searchBookCounts()` (GROUP BY book_id ORDER BY count DESC — для Book sheet). `SearchViewModel.loadMore()` довантажує сторінку, коли на екран виходить один з останніх 10 рядів (prefetch, синхронний виклик на MainActor — той самий бюджет ~ms).
2. **Фільтри переїхали в SQL** — клієнтський `filteredResults` видалено (з пагінацією він не працює). Зміна будь-якого фільтра на сторінці результатів перезапускає committed query.
3. **Chip-бар замість segmented control** (патерн YouVersion): три капсули над результатами — Translation / Testament (СЗ⁄НЗ) / Book — кожна відкриває sheet. Активний (не-дефолтний) фільтр = `.borderedProminent`. Розміщення успадковане: iOS 26 `.safeAreaBar(edge: .top)`, iOS 18 pinned section header; бар видимий і на порожньому стані (щоб можна було послабити фільтри).
4. **Translation-фільтр — локальний для пошуку.** Дефолт = переклад рідера (`selectedTranslationId == nil` → follow reader); вибір у пошуку рідер НЕ перемикає. Реюз `DefaultTranslationPickerView` (MenuView) через Binding + новий параметр `titleKey`. ViewModel сам вантажить `loadBookNames(for:)` пошукового перекладу — референси й назви книг у Book sheet йдуть у нативних іменах перекладу пошуку, не рідера.
5. **Book-фільтр залежить від Testament:** sheet показує книги лише вибраного заповіту, впорядковані за кількістю збігів (YouVersion), з count поруч; зміна заповіту скидає несумісну вибрану книгу.

**Аналітика:** `search_committed.resultsCount` тепер = повний COUNT (без кепа 150); `search_result_opened.resultsCount` = той самий фільтрований total з хедера, `position` = індекс у довантаженому списку. `resultsCapped` видалено.

**Не змінюється:** FTS5 схема, `search_terms`, предіктів-модель (amendment 2026-06-11), debounce 280ms. Борг per-translation `search_terms` (крок B) лишається відкритим.

## Amendment 2026-08-06 — у FTS іде очищений текст, а не сирий `verse.text` (bug-035)

**Контекст:** тестер повідомив, що пошук із двох слів не знаходить нічого, хоча кожне слово окремо знаходиться: `долиною` дає Пс 22:4, `смертной тени` — порожньо, хоч ці слова стоять поруч у тому самому вірші.

Причина — на стику двох рішень, кожне з яких окремо правильне. Пункт 1 Decision вище будує індекс з `content='verse'`, тобто FTS5 читає **сирий** `verse.text`, а `_clean_verse()` у `build_db.py` навмисно **зберігає** `<S>1234</S>` — їх потребує app-парсер для word-study. Токенайзер `unicode61` про XML не знає й ріже `<S>6757</S>` на токени `S | 6757 | S`. `DatabaseService.makeFTSQuery()` обгортає ввід у лапки (`"смертной тени"*`), а це **фразовий** запит — вимога, щоб токени стояли впритул. Між двома словами стояло три чужі токени.

Запит з одного слова — це фраза з одного токена, сусідів не потребує. Тому баг читався як «не працює пошук з кількох слів», а не «не працює пошук», і прожив непоміченим від самого початку.

**Заміряно** на `data/RST+.zip` (Пс 22:4, 9 `<S>`-тегів у вірші), in-memory FTS5 з тим самим токенайзером: `"долиною"*` → 1 в обох варіантах; `"смертной тени"*` → **0** по сирому тексту, 1 по очищеному.

**Обсяг ширший, ніж перший симптом:** биті всі теговані переклади (KJV/ASV/NASB/RST), а ріже фразу **будь-який** тег усередині вірша, не лише `<S>`. Перевірено на `<J>` (слова Христа): `"сказал Я"` і `"есмь путь"` дають 0, тоді як `"Я есмь"` цілком усередині тега дає 1. В Огієнка (`strong_numbers=false`) фрази здебільшого працюють, але ламаються об `<i>`/`<n>`.

**Рішення:**

1. **Нова колонка `verse.text_clean`** — копія `text` без будь-якої розмітки, дзеркало `String+BibleMarkup.strippingBibleMarkup()`. `<S>N</S>` знімається **разом із числом**: зняти лише теги недостатньо, цифри лишаються словами.
2. **`verse_fts` будується над `text_clean`.** `content='verse'` лишається — індекс і далі не дублює текст. Колонка 0 індексу та сама, тож `highlight(verse_fts, 0, …)` у `searchByText()` не змінився; тепер він повертає вже чистий текст, а `.strippingBibleMarkup()` на сніпеті лишається no-op-запобіжником.
3. **`build_search_terms()` читає `text_clean`.** Побічний дефект того ж кореня: стара версія знімала теги регуляркою `<[^>]+>`, але цифри Стронга лишались словами — заміряно на самому RST, 7 753 з 30 660 термів (25.3%) були чисті числа, `3588` × 19 048. Чверть автокомпліту пропонувала номери Стронга як слова.
4. **`verify_search_index()` у `build_db.py`** після побудови індексу, ненульовий вихід. Якорі **двослівні** — односкладовий матчився й на зламаному індексі, тож нічого б не довів. Плюс контрольні фрази, які мусять давати **нуль** (`тени долиною` — ті самі слова, зворотний порядок), щоб ловити протилежну помилку, коли сусідство перестає перевірятись. Переклад, якого в білді немає (NASB/UBIO — ліцензійні), пропускається, а не валить збірку.
5. **`scripts/tests/test_search_index.py`** — 13 кейсів, без мережі й бази. Серед них `test_raw_index_reproduces_the_bug`: будує індекс по сирому тексту й вимагає, щоб фраза **не** знаходилась. Якщо колись пройде навпаки — діагноз був хибний, і фікс стоїть на неправильному поясненні.

**Інваріант — має пережити наступні рефактори:**

> `verse.text` — джерело для парсера, теги зберігаються. У FTS іде **тільки** `text_clean`. Індексувати сирий `verse.text` = ламати фразовий пошук.

**Ціна:** одна текстова колонка в `verse` (оцінка ~20 МБ, не заміряно) і повна перезбірка — колонка пишеться на імпорті перекладів, тож `./rebuild.sh`, не міграція.

**Відхилено: `NEAR("смертной" "тени"*, 4)` замість фрази в `makeFTSQuery`.** Працює без перезбірки бази (перевірено, дає 1) — тому й записано тут, щоб не перевідкривали як дешевшу альтернативу. Не тримає **порядок** слів (`тени долиною` матчиться), вікно треба закладати з запасом на кожну міжслівну межу, а сміттєві токени лишаються в ранжуванні BM25. Прийнятне лише як тимчасовий хотфікс, якщо білд треба віддати тестерам раніше, ніж перезібрати базу — і тоді цей амендмент має описувати обидва стани, інакше документ каже одне, а код робить інше.

**Не змінюється:** токенайзер, `content='verse'`, пагінація й фільтри (amendment 2026-07-07), предіктів-модель (amendment 2026-06-11), debounce 280ms, `makeFTSQuery` (фразова семантика лишається). Борг per-translation `search_terms` (крок B) досі відкритий.


## Amendment 2026-08-07 — канонічний порядок видачі + словник підказок по МОВІ, не спільний

**Привід:** коротке інтерв'ю з користувачем (2026-08-06) виявило два дефекти, які до того жили як «так і має бути».

### 1. Порядок результатів був невиводимий для читача

`ORDER BY rank, verse_fts.rowid` — BM25. Оцінка залежить від рідкості слова в корпусі й довжини вірша, тож на запит «Душа» видача починалась Пр. 13:4, далі Єз. 18:4, 3М. 7:27, знову Пр. 19:15. Для читача це шум: жодного порядку, який можна тримати в голові, і неможливо сказати «я вже проглянув Тору». BM25 виправданий там, де корпус різнорідний і релевантність справді ранжується; у Біблії всі 31 тис. віршів однакового жанру й ваги, а «релевантність» вироджується в довжину вірша.

**Рішення: канонічний порядок — книга → глава → вірш.** Ранжування прибрано, не приховано за перемикачем: перемикач тут довелось би пояснювати, а BM25-режим не має жодного випадку, в якому б виграв.

**Порядок книг — per-translation, НЕ `book.num`.** Заміряно: у RST 21 книга стоїть інакше — соборні послання (Як., 1–2 Пт., 1–3 Ів., Юд.) ідуть **перед** Павловими (Рим.…Євр.), як у синодальній традиції. `book.num` дав би RST-читачеві протестантський порядок, тобто в межах його ж перекладу видача б суперечила рідеру (ADR-018). Тому:

```sql
LEFT JOIN book_name bn ON bn.book_id = v.book_id AND bn.translation_id = v.translation
ORDER BY COALESCE(bn.sort_order, b.num - 1), v.chapter, v.verse
```

`LEFT JOIN` + `COALESCE` — навмисно: `INNER JOIN` **втрачав би результати** для (книга, переклад) без рядка в `book_name`. Зараз покриття повне (66 × 5, віршів без рядка = 0), але схема цього не гарантує, а тихо зникла книга — гірший дефект за неправильний порядок.

**Побічно швидше**, а не дорожче — заміряно на живій базі (десктопний CPU у пісочниці, не пристрій; тримається відношення, не абсолют):

| запит | `ORDER BY rank` | канонічний |
|---|---|---|
| `"душа"*` UBIO | 1.32 ms | 0.83 ms |
| `"і"*` UBIO (21 516 збігів) | 29.6 ms | 21.3 ms |
| `"the"*` KJV | 63.7 ms | 47.4 ms |
| `"і"*` UBIO, OFFSET 2000 | 83.7 ms | 33.5 ms |

Причина: BM25 треба порахувати для кожного збігу, `sort_order` — прочитати. Найбільший виграш саме на глибокому OFFSET, тобто в нескінченному скролі. Тайбрейк `verse_fts.rowid` більше не потрібен: (книга, глава, вірш) унікальні в межах перекладу, тож пагінація детермінована за побудовою.

### 2. Підказки змішували мови — бо словник один на всі переклади

`build_search_terms()` читав `SELECT text_clean FROM verse` **без** `WHERE translation`, тобто `search_terms` — одне частотне ведро на п'ять перекладів. Симптом, який побачив користувач (заміряно, не з пам'яті):

```
се*   → себе, себя, сердце, серед, сего, серце, сей, семь     ← ru та uk через рядок
душ*  → душа, душу, души, душі, душею, душ, душе, душах
```

Тихіший, гірший симптом того ж кореня: підказка може привести до запиту з **нулем** результатів — слово існує в RST, а `searchByText` фільтрує `AND v.translation = ?` і шукає в UBIO. Тобто підказки й пошук працювали над різними множинами.

**Рішення: `search_terms(term, lang)`, ключ по МОВІ, не по перекладу.** Розбіжність із боргом «per-translation `search_terms`», записаним в амендментах 2026-07-07 і 2026-08-06 — свідома: per-translation дав би три майже однакові англійські словники (KJV/ASV/NASB перекриваються), а мовна каша від цього не зникає, бо вона між мовами, а не між перекладами. Заміряно обидва варіанти:

| | зараз (спільна) | per-translation (борг) | **per-language (обране)** |
|---|---|---|---|
| рядків | 60 174 | 74 329 | **61 776** |
| розмір у бандлі | 1 300 KB | 1 860 KB | **1 532 KB** |
| приріст | — | +560 KB | **+232 KB** (+0.07% від 342 MB) |

Швидкість — краща, не гірша: `translation`/`lang` відсікає кандидатів **до** сортування, а `USE TEMP B-TREE FOR ORDER BY freq` і є єдине місце, де тут можна лагати. Індекс той самий префіксний скан по PK (`SEARCH USING PRIMARY KEY (term>? AND term<?)`).

| префікс | зараз | per-language |
|---|---|---|
| `а` (uk) | 0.335 ms | 0.113 ms |
| `l` (en) | 0.199 ms | 0.087 ms |
| `го` (ru) | 0.187 ms | 0.078 ms |
| `душ` (uk) | 0.031 ms | 0.032 ms |

Тобто найгірший випадок (короткий префікс = максимум кандидатів) втричі швидший, а на довгих різниця в межах шуму.

**Головне — масштабування.** Мова джерела: `translation.language` (`en`/`ru`/`uk`), уже в схемі. Додавання німецької чи іспанської тепер **не змінює нічого**: новий переклад приносить свою мову, словник розділяється сам. Зі спільною таблицею кожна нова мова вливалася б у ту саму кашу, і чим більше мов — тим менше шансів, що правильна підказка втримається у `LIMIT 8`.

**Перекриття мов НЕ є аргументом проти розділення:** ru ∩ uk = 2 049 термів на об'єднанні 43 602 (4.7%). Дублювання тих 4.7% дешевше за помилку в підказці.

**Перевірки в коді (правило «перевірки — у код, не в очі»), ненульовий вихід:**

1. **Якорі розділення** — `этого`/`который`/`чтобы` мусять бути в `ru` і **не бути** в `uk`; `цього`/`якого`/`щоб`/`нього` — навпаки. ⛔ `него` як якір НЕ використовувати: воно є в обох (Огієнко теж його вживає), тобто перевірка на ньому пройшла б і на зламаному розділенні.
2. **Кожна мова з `translation` має непорожній словник** — інакше мовчазний нуль підказок для цілого перекладу.
3. **Стеля числових термів** (`_NUMERIC_TERM_CEILING`, з amendment 2026-08-06) — рахується тепер **на мову**, бо сумарна частка ховала б перекіс в одній.

**Не змінюється:** FTS5-схема й токенайзер, `text_clean`-інваріант, фразова семантика `makeFTSQuery`, debounce (280 ms пошук / 120 ms підказки), фільтри й пагінація, `searchBookCounts` (Book sheet і далі за кількістю збігів — там сортування за релевантністю доречне, це вибір фільтра, а не читання).

**Борг закрито:** «per-translation `search_terms` (крок B)» більше не відкритий — рішення прийнято на користь per-language. Не відроджувати per-translation.

**Ціна:** перезбірка `search_terms` (~2.5 с) — колонка не чіпає `verse`, тож повний `./rebuild.sh` не потрібен.

## Rejected Options

- **ObjectBox** — міграція ORM без ROI для read-only bundle.
- **GRDB.swift** — не потрібен без sqlite-vec (системний SQLite має FTS5).
- **sqlite-vec + ONNX Runtime Mobile** — V1.5; +2-3 дні складності, якість ембедингів невідома без тестування.
- **Stanza/VESUM лематизація** — defer до V1.5 разом з vector search.

## Trade-offs

| Що маємо | Що відкладаємо |
|---|---|
| Working search за 4 год | Semantic search "смуток → Йов" |
| Zero нових залежностей | Морфологічний стемінг для укр. |
| 100% offline | — |
| Strong's/lemma через word tap (ADR-013/016) | Strong's/lemma у search-барі — виключено, не буде |

## Upgrade Path (V1.5)

1. `build_db.py`: `build_verse_vectors()` — `sentence-transformers` → ONNX INT8 → `vec0` virtual table (~47MB).
2. iOS: `sqlite-vec` SPM пакет + ONNX Runtime Mobile (~30MB, all-MiniLM-L6-v2 або fine-tuned на cross_reference pairs).
3. `DatabaseService.searchByVector()` → новий метод, existing architecture не змінюється.
4. `SearchMode.semantic` → додається до enum без рефакторингу.
