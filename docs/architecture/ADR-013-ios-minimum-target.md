# ADR-001: Мінімальна версія iOS для Source Bible App

**Статус:** Proposed  
**Дата:** 2026-05-05  
**Область рішення:** Платформа / Deployment Target  
**Контекст:** MVP Source Bible App (React Native), pre-development stage

---

## Контекст

Проект знаходиться на стадії pre-development (UI-прототип готовий, BRD затверджено).
Поточний BRD визначає вимогу `Works on iOS 15+`. Паралельно надійшло питання
про альтернативний підхід — спочатку зібрати MVP для iOS 18, а потім додати підтримку
iOS 15 для покриття потенційних втрат ринку.

Рішення, яке ми оцінюємо: **iOS 18 для MVP → iOS 15 бекпорт у наступній ітерації**.

Ринковий контекст (з аналітичного документа, весна 2026):
- Глобально: ~90% активних iPhone вже на iOS 18+, ~10% — нижче
- Україна: ~89–91% на iOS 18+, ~9–11% ризик втрат
- Planning stress-case: 100 млн користувачів глобально при базі 1 млрд

---

## Технічний стан стека

Перш ніж порівнювати опції, важливо зафіксувати реальний стан React Native.

| Версія React Native | Мінімальна iOS | Примітки |
|---|---|---|
| 0.73 | iOS 13.4+ | — |
| 0.74 | iOS 13.4+ | — |
| 0.75 | iOS 15.1+ | Dropped iOS 13 |
| 0.76 (поточна стабільна) | iOS 15.1+ | New Architecture за замовчуванням |
| 0.77+ | iOS 15.1+ | — |

**Ключовий висновок:** React Native 0.76 (поточна стабільна) вже вимагає iOS 15.1+ як власний
мінімум. Це означає, що "iOS 15 backport" — це не зниження нижче можливого, а повернення
до нижньої межі самого фреймворку.

## Аналіз фіч MVP і їх iOS-залежностей

| Фіча (з BRD) | iOS-залежна API | Мінімальна iOS для API | Примітка |
|---|---|---|---|
| Bible Reader (scroll, text) | UIScrollView, UILabel | iOS 2+ | Без обмежень |
| Bottom sheet | UISheetPresentationController | **iOS 15** | Saме поріг RN 0.76 |
| Voice search (🎤) | Speech framework | iOS 10+ | Без обмежень |
| AI semantic search | HTTP/URLSession | iOS 7+ | Backend call |
| Strong's data / concordance | SQLite / API call | iOS 3+ | Без обмежень |
| Notes / Bookmarks | Core Data / API | iOS 3+ | Без обмежень |
| Firebase | iOS 13+ | — | Запас |
| RevenueCat | iOS 11+ | — | Запас |
| Sentry (якщо обрати) | iOS 13+ (v8); iOS 15 (v9 alpha) | — | Перевірити версію |
| Dark mode / Typography | UITraitCollection | iOS 13+ | Без обмежень |

**Висновок по фічам:** Жодна фіча MVP не вимагає iOS 16, 17 або 18. Нижня межа,
продиктована самими фічами і поточним React Native, — **iOS 15.1**.

Єдині iOS 18-exclusive API, що могли б мати значення для цього типу продукту:
- **Writing Tools** (AI-рефайнінг тексту) — поки що out of scope навіть у V2
- **Apple Intelligence** — вимагає iPhone 15 Pro / 16, не лише iOS 18; у Китаї обмежено

## Порівняння опцій

### Опція A: iOS 18 → потім iOS 15 бекпорт (пропонована)

**Phase 1 — MVP під iOS 18**

Що це означає технічно:
- Зміна `IPHONEOS_DEPLOYMENT_TARGET` з 15.1 до 18.0 у Xcode project settings
- Більше нічого — жодних фреймворкових змін, жодних нових API

| Параметр | Оцінка |
|---|---|
| Складність реалізації | **Низька** — одна зміна в Xcode |
| Технічна перевага | **Відсутня** — MVP-фічі не потребують iOS 18 API |
| Тестова матриця | Спрощена: лише iOS 18.x (симулятор + 1-2 девайси) |
| Ризик MVP-валідації | **Середній** — штучно звужена аудиторія |
| Час розробки MVP | Без змін відносно iOS 15 |

**Phase 2 — iOS 15 бекпорт**

| Параметр | Оцінка |
|---|---|
| Складність | **Низька → Середня** (залежить від того, що накопичилось у native-коді) |
| Зміна deployment target | `18.0` → `15.1` в Xcode |
| Аудит native modules | Пошук `#available(iOS 16, *)` та вище в bridge-коді |
| Expanding test matrix | +iOS 15.x симулятор, перевірка bottom sheet, шрифти |
| Орієнтовний спринт | 1–2 спринти (audit + QA) |
| Ризик | Якщо хтось зі стек використав iOS 16/17 API у custom native module без `#available` — refactor |

**Загальна складність Опції A:** Низька на Phase 1 + Низька/Середня на Phase 2  
**Ринковий ризик під час MVP:** ~9–11% потенційних користувачів недоступні на старті

---

### Опція B: iOS 15.1 з дня першого (поточний BRD)

| Параметр | Оцінка |
|---|---|
| Складність реалізації | **Низька** — дефолт RN 0.76 |
| Технічна перевага | Повна аудиторія iOS 15+ від старту |
| Тестова матриця | iOS 15.x + 16.x + 17.x + 18.x — ширша, але стандартна |
| Ринковий ризик | **Мінімальний** — покриваємо ~90%+ бази |
| Бекпорт пізніше | Не потрібен |

---

### Опція C: iOS 18 як постійний мінімум (без бекпорту)

| Параметр | Оцінка |
|---|---|
| Складність | Найнижча |
| Виправдано для Source Bible? | **Ні** — жодна MVP-фіча цього не вимагає |
| Ринкові втрати | ~9–11% по Україні, ~10% глобально |
| Резонність | Виправдана лише якщо є конкретна iOS 18-exclusive фіча в core value |

## Trade-off Analysis

### Чому Опція A (iOS 18 → iOS 15) виглядає привабливою, але має приховані витрати

1. **Немає технічного драйверу.** У React Native мінімальний deployment target — це Xcode-рядок,
   а не зміна архітектури. Спрощення від "iOS 18 only" на фазі MVP — ілюзорне.
   Тест-матриця справді менша, але різниця — 2–3 додаткові симулятори.

2. **Ринковий ризик під час валідації.** Якщо ви відкидаєте ~10% потенційної аудиторії
   на фазі MVP, ваші метрики (retention, conversion, DAU) будуть зміщені на більш tech-savvy
   когорту. Рішення "чи робити бекпорт" прийматимете по скошеній вибірці.

3. **Цільова аудиторія Source Bible не є early-adopter сегментом.** Christians 20–50+,
   зокрема пастори і лідери малих груп — ця когорта ближча до Apple's 10% estimate,
   ніж до TelemetryDeck's 4.31% (який скюється до indie/tech apps). Саме ваш ринок
   матиме вищий відсоток iOS <18, ніж середній productivity-app.

4. **Для бекпорту пізніше все одно потрібен QA-цикл.** Навіть "мінімальний" бекпорт —
   це спринт тестування + потенційні фікси + CI pipeline зміни. Не нульові витрати.

5. **Єдине реальне виправдання Опції A:** Якщо ви плануєте у V2 використати конкретну
   iOS 18+ API (наприклад, Writing Tools для AI-коментарів, або Live Activities для
   reading streak), і хочете зробити MVP "нативним" під цей API — тоді можна почати
   з iOS 18 і свідомо не нести backcompat-техдолг. Але у поточному BRD таких фіч немає.

## Рекомендація

**Обрати Опцію B: iOS 15.1 як мінімум з дня першого.**

Обґрунтування для Source Bible App конкретно:

- React Native 0.76 вже floor'ує на 15.1 — це не компроміс, це норма фреймворку
- Жодна фіча MVP не потребує iOS 16/17/18 API
- Цільова аудиторія (релігійний контент, 20–50+, Україна як один з ринків) з вищою
  ймовірністю має старіші пристрої, ніж tech-focused аудиторія
- MVP — це фаза перевірки гіпотези. Штучне звуження аудиторії спотворює дані
- Після MVP у вас будуть власні цифри: MAU по OS major, payer share по OS. Тоді можна
  ухвалити обґрунтоване рішення про підняття мінімуму до iOS 16/17/18 — з реальними даними

**Якщо iOS 18 мінімум все ж обирається:** ухваліть це як постійне рішення (Опція C),
а не як тимчасове з наміром бекпорту. Бекпорт після — гірший варіант: він додає витрати
і без реального виграшу на фазі MVP.

## Матриця тестування при Опції B (iOS 15.1+)

| Рівень | Що покривати |
|---|---|
| Smoke | iOS 15.x на найстарішому підтримуваному пристрої (iPhone XR/SE 2nd gen) |
| Primary | iOS 18.x на A16/A17 класі + iOS 26 (beta / early adopters у вашій аудиторії) |
| Revenue critical | onboarding → paywall → purchase → restore → renewal |
| Bottom sheet | Поведінка UISheetPresentationController на iOS 15 vs 18 |
| Stability | Low-memory (старі девайси), offline / poor network, background state |
| Compliance | ATT prompt, account deletion, accessibility (Dynamic Type XL) |

## Fallback і міграційний план (якщо обрано B)

```
Q2 2026 — MVP під iOS 15.1
  • Встановити IPHONEOS_DEPLOYMENT_TARGET = 15.1 у Xcode
  • Збір базових метрик: MAU по OS major, install mix по OS

Q3 2026 — Аналіз даних
  • Якщо iOS <16 < 5% MAU — запланувати підняття мінімуму до iOS 16 у наступному циклі
  • Якщо iOS <16 > 8% MAU або > 10% revenue — залишити поріг на 15.1

Q4 2026 / Q1 2027 — Можливе підняття мінімуму
  • На основі реальних даних прийняти data-driven рішення
  • Graceful unsupported-OS screen + deep link у Settings → Software Update
```

## Відкриті питання (до фіналізації)

- [ ] Expo або bare workflow? (впливає на деякі native module floor'и)
- [ ] Чи планується Live Activities / Widget для reading streak у V2? → аргумент для iOS 16+
- [ ] Яка частка iOS <18 у власній аналітиці прототипу (якщо є TestFlight)?
- [ ] Регіональний фокус MVP: якщо старт тільки на США/UK — Опція C (iOS 18 only) стає
  обґрунтованою (94–95% покриття), якщо Україна входить у старт — лишайтеся на 15.1

## Consequences

Якщо обрати Опцію B (рекомендовано):
- ✅ Максимальна addressable audience під час MVP-валідації
- ✅ Немає додаткового QA-циклу для бекпорту
- ✅ Метрики MVP відображають реальну аудиторію
- ✅ React Native 0.76 New Architecture повністю сумісна з iOS 15.1+
- ⚠️ Ширша тест-матриця: потрібен iOS 15.x симулятор у CI
- ⚠️ Не можна безоглядно використовувати iOS 16/17 API у native modules без `#available`

Якщо все ж обрати Опцію A:
- ✅ Вузька тест-матриця на Phase 1
- ✅ Можна вільно використовувати iOS 18 API без guards
- ❌ ~10% потенційних users виключено під час валідації
- ❌ Додатковий спринт на бекпорт (Phase 2) без гарантованого ROI
- ❌ Ризик "назавжди відкладеного бекпорту" через backlog-тиск
