# ADR-027 — Модульні commentary-модулі з OTA-оновленням

**Status:** Proposed (2026-07-05)
**Depends on:** ADR-028 (Версифікація — `verse_org` як єдине джерело версифікації; модулі якоряться в org ЧЕРЕЗ нього)
**Related:** ADR-012 (Unified User Data Layer — writable GRDB, sync-ready), ADR-008 (Search — FTS5 у ядрі), ADR-006 (Localization — upgrade path Bundle→DB→Remote), ADR-029 (переклади → ядро, коментарі → модулі; те саме розрізнення), `commentary-system-design.md`, `scripts/import_commentaries.py`, `docs/db_build.md`
**Замінює/уточнює:** модель доставки коментарів у монолітному `sourcebible.db`

---

## Контекст

Зараз **усі** дані бандляться в один `sourcebible.db`: ядро (`word` Macula, `verse`, `strongs`, `verse_org`, `cross_reference`, `book`, `translation`) **разом** із коментарями (`comments`, `comment_verses`). Збірка — `build_db.py` (~10 хв) + `build_versification.py` (`verse_org`, ADR-028) + `import_commentaries.py` (Calvin/Henry/Spurgeon/Owen) + `process_glosses.py`. База — APFS sparse (~24 МБ фізично / ~149 МБ логічно).

Це створює три проблеми, виявлені на практиці:

1. **Будь-яка правка коментаря тягне перезбірку/патч усього.** Дірка в одному творі (напр. виявлено: **Кальвінова Ісая обривається на гл. 48** у SWORD-джерелі `CalvinCommentaries.zip` — глав 49–66 нема взагалі; плюс у MyBible-модулях знайдено діри в Буття 10–30, Іван 6, і 5 сміттєвих псевдо-книг) вимагає або патч-скрипта, або 10-хв прогону, хоча Macula/Strongs/переклади не змінювались.

2. **Оновлення контенту прив'язане до релізу застосунку.** Виправив текст — чекай на App Store review. Для контенту (особливо **машинного перекладу**, який за природою «випусти зараз, вичитуй ітеративно») це неприйнятно повільний цикл.

3. **Ліцензійні межі — логічні, а не фізичні.** Owen (Hebrews) має обмеження «безкоштовно можна, у платний тариф — ні» (див. `import_commentaries.py` licensing note). У моноліті це рядки, які треба вирізати; хочеться — окремий файл, який просто не кладеться в платну збірку.

## Рішення

**Винести коментарі з моноліту в окремі read-only SQLite-модулі, оновлювані OTA незалежно від релізу застосунку. Ядро (Macula/verse/strongs/xref) лишається монолітом.**

- **Одиниця доставки — твір автора** (Calvin, Henry, Spurgeon, Owen…), кожен — окремий `.db`-файл.
- **Одиниця оновлення — книга** всередині твору (вичитав Ісаю → пушиш лише Ісаю), щоб дельти на мобільному трафіку були дрібні без diff-механіки.
- **Ядро не дробимо.** Macula/verse/strongs — велике, повільне, майже незмінне. Уся вигода від модульності — саме в коментарях (міняються + мають діри).
- Застосунок читає ядро + встановлені модулі через `ATTACH DATABASE`; реєстр встановлених модулів (`installed_modules`) у writable-шарі (ADR-012).

### Майстер ≠ артефакт (обов'язкове розділення)

| Шар | Формат | Де живе | Призначення |
|---|---|---|---|
| **Майстер-джерело** | структурований текст (Markdown або JSONL, 1 запис = авторський розділ) + `provenance` | git / хмара | джерело правди; вичитка, ревʼю, merge джерел, історія змін (diff!) |
| **Модуль-артефакт** | read-only SQLite | збірка → CDN / бандл | доставка в застосунок |

`.db`-модуль — **похідне**. Бекапиться й версіонується **майстер**; `.db` завжди перезбирається з нього. Зберігати в хмару лише `.db` = бекап артефакту без джерела (правки й історію не відновиш).

### Жорсткі інваріанти дизайну

1. **Секції якоряться в оригіналі (org) ЧЕРЕЗ `verse_org` (ADR-028) — модуль НЕ носить власної версифікації.** `verse_org` — тотальний курований міст «вірш перекладу ⇄ вірш оригіналу» (org = Macula: MT для СЗ, грец. для НЗ); мапінг НЕ виводиться наново (правило ADR-028 «never re-derive mapping»).
   - **Build-time:** рідне посилання джерела (SWORD OSIS ≈ `eng`-схема; MyBible `russian_numbering` ≈ `rso`) → reverse через `verse_org` → координата org. Так класичний зсув (напр. заголовки Псалмів = вірш 1 у MT) лікується сам.
   - **Runtime:** юзер читає переклад T, тапає вірш → forward `verse_org` `(T,book,ch,v)`→`org_*` → секція, заякорена на org. Версифікація-агностично для будь-якого перекладу (KJV/RST/Огієнко), однаковий шлях, що й «Оригінал»/крос-рефи.
   - **`org = NULL`** («немає оригіналу») → fallback-індекс на координату конкретного перекладу (рідко для 66 книг, але правило обов'язкове). **N:M/крос-глава** → `comment_verses` розкладається на кілька рядків індексу на той самий `key`.

2. **Стабільні природні ключі, НЕ `rowid`.** Ідентичність розділу = `source + book_id + start_ch:start_vs–end_ch:end_vs` (стабільний хеш). Перезбірка/виправлення тексту **не змінює** ідентичність. Інакше зсув `rowid` ламає все, що посилається на розділ (закладки, «продовжити», cross-ref).

3. **Дані користувача — поза модулем.** Підсвітки/нотатки (writable GRDB, ADR-012) посилаються на розділ через стабільний ключ і **ніколи не лежать усередині замінного модуля** — інакше оновлення їх зітре. (ADR-012 уже розділяє read-only bundle і writable user data — цей інваріант його продовжує.)

4. **Атомарна заміна з перевіркою.** Качання: temp-файл → перевірка checksum (SHA-256; криптопідпис — fast-follow, не MVP, див. Amendment 2026-08-28 нижче) → атомарний swap → стару версію тримати до валідації для відкату. Не редагувати файл «на місці», поки застосунок із нього читає (урок побитих sparse-баз, `db_build.md`).

### Схема модуля (стабільний контракт)

```sql
-- у кожному <author>.commentary.db
comments(
    key            TEXT PRIMARY KEY,   -- стабільний: hash(source|book|range)
    source         TEXT,               -- 'Calvin'
    book_id        TEXT,               -- org_book_id (USFM 'ISA'), НЕ MyBible book_number
    start_chapter  INTEGER, start_verse INTEGER,
    end_chapter    INTEGER, end_verse   INTEGER,   -- КООРДИНАТИ ORG (Macula), отримані через verse_org на збірці
    text           TEXT,
    -- provenance / статус (критично для MT-циклу):
    origin         TEXT,               -- 'SWORD:CalvinCommentaries' | 'MyBible:Calvin-c' | 'CCEL'
    translation_status TEXT,           -- 'source' | 'raw-mt' | 'reviewed' | 'final'
    reviewer       TEXT, reviewed_at   TEXT
)
comment_verses(key TEXT, book_id TEXT, chapter INTEGER, verse INTEGER)  -- індекс в ORG-координатах; runtime: reader-translation → verse_org → org → key. org=NULL → окремий translation-anchored fallback-індекс
module_info(name, value)  -- author, version, schema_version, min_app_version, book_versions(JSON)
```

`translation_status` = і робочий трекер вичитки, і можливість чесно показати юзеру «машинний переклад, можливі помилки», поки книга не пройдена людиною (узгоджується з trust-rule: LLM-контенту довіряємо обмежено).

*(Amendment 2026-09-01 додав `language` до цієї схеми і уточнив семантику `translation_status` — див. розділ нижче.)*

### Оновлення: маніфест + статичне сховище (без сервера)

- У хмарі (S3/R2/будь-яке об'єктне сховище) — `manifest.json`: для кожного `author/book` версія + URL + checksum.
- Клієнт при старті звіряє встановлені версії з маніфестом → показує/качає доступні оновлення.
- Інфраструктура = статичні файли, **не** сервер-логіка. Дешево, кешовно, надійно. (Паралель до ADR-006 upgrade path → Remote.)

### Межа bundle vs download

- Дефолтний набір (напр. Calvin+Henry) — **бандлиться** з застосунком (працює offline з коробки).
- Решта — **докачується** на вимогу (менший стартовий розмір, юзер бере що хоче).
- Докачані модулі — в app Documents dir; ядро й дефолт — у bundle.

## Відкриті питання — ЗАКРИТО (Amendment 2026-08-28)

Усі чотири питання нижче мали статус «треба рішення перед імплементацією». Архітектурна сесія 2026-08-28 закрила всі чотири; повне обґрунтування — в Amendment нижче.

- ~~**Схема модуля: власна канонічна vs MyBible-сумісна.**~~ **Підтверджено: власна канонічна + окремий імпортер MyBible.** Рекомендація ADR не просто прийнята — виявилась обов'язковою після перевірки реального MyBible-контракту в `build_db.py` (`book_number` позиційний, не стабільний; координати версифікаційно-відносні, не org-anchored; немає provenance/status). Деталі → Amendment §1.
- ~~**FTS5-пошук через модулі.**~~ **Підтверджено: варіант (a)** — власна FTS5-таблиця на модуль + `UNION ALL` по `ATTACH`, перевірено емпірично (SQLite-спайк). Варіант (b) фізично неможливий: FTS5 `content=` мусить бути в тій самій БД, що й сама FTS5-таблиця. Деталі, включно з виміряним лімітом `ATTACH` → Amendment §2.
- ~~**Дельти всередині книги.**~~ **Підтверджено: відкласти, з конкретним вимірюваним тригером** (замість розмитого «якщо трафік стане проблемою»). Деталі → Amendment §3.
- ~~**Підпис модулів.**~~ **Підтверджено: MVP = checksum (SHA-256) + HTTPS-джерело; криптопідпис — за конкретного тригера** (поява sideload/маркетплейсу), не «fast-follow» безрозмірно. Деталі, включно зі знайденою внутрішньою суперечністю в тексті ADR → Amendment §4.

## Обсяг (орієнтовно; поетапно)

1. **Схема + майстер + provenance** — визначити канонічну схему модуля, формат майстра, поля provenance/статусу. Спроєктувати генератор `master → module.db`.
2. **Пілот на Кальвіні** — зібрати `calvin.commentary.db` окремо; закрити діру Ісая 49–66 (майстер: SWORD 1–48 + MyBible 49–66, нормалізовані); аудит решти книг пословно. **Ревізія джерел 2026-08-28** (`docs/commentary-sources-audit.md`) уже почала цей аудит: Ісая 49–66 виявилась повною в самому MyBible-джерелі (без потреби в SWORD-splice); Генрі (живий парсер порожній на 19.8% глав, 17 книг) і Оуен (парсер ніколи не читає вступ+огляди по главі) мають ще серйозніші розбіжності зі своїми MyBible-кандидатами, кожна зі своєю відомою дірою (Луки 16:19-31 у нового Генрі, Євр. 1:1-2 у нового Оуена) — латати перед заміною джерела, не після.
3. **Рантайм** — `ATTACH DATABASE`, реєстр модулів, lookup через стабільні ключі, FTS-рішення.
4. **OTA** — маніфест, звірка версій, temp→verify→swap→rollback, UI «доступні оновлення».
5. **Імпортер MyBible** (опц.) — нормалізація сторонніх модулів у канонічну схему.

## Trade-offs

- **(+)** Правка контенту без релізу застосунку; дрібні per-book оновлення; MT-цикл «випусти→вичитуй» стає швидким.
- **(+)** Перезбірка одного твору за секунди замість 10-хв моноліту.
- **(+)** Ліцензійні межі фізичні (Owen = окремий файл, не кладеться в платну збірку).
- **(+)** Provenance/статус на розділ — трекер вичитки + чесність щодо MT.
- **(−)** Складніший рантайм: `ATTACH`, реєстр, звірка версій, OTA-протокол (temp/verify/swap/rollback).
- **(−)** FTS через кілька модулів — нетривіально (див. відкрите питання).
- **(−)** Дисципліна майстер↔артефакт і стабільних ключів — треба тримати суворо, інакше OTA ламає посилання/аннотації.

## Amendment 2026-08-28 — рішення по чотирьох відкритих питаннях

Архітектурна сесія без зміни коду (CLAUDE.md правило #1: аналіз/рішення — так, Swift/скрипти/БД — ні). Мета — закрити відкриті питання перед імплементацією. Прочитано: ADR-028 (verse_org), ADR-012 (writable GRDB), ADR-008 (FTS5, включно з amendment 2026-08-07 про відмову від BM25), ADR-006 (Bundle→DB→Remote), ADR-029 (переклади в ядрі vs коментарі в модулях), `commentary-system-design.md`, `scripts/import_commentaries.py`, `scripts/build_db.py`.

### §1 — Схема модуля: власна канонічна, підтверджено

`scripts/build_db.py` (крок 6) уже парсить реальну MyBible commentary-схему:

```sql
commentaries(book_number, chapter_number_from, verse_number_from,
             chapter_number_to, verse_number_to, marker, text)
```

Три факти з цього ж коду роблять «взяти MyBible-схему як наш OTA-контракт» непрацездатним варіантом, не лише «менш чистим»:

1. **`book_number` — позиційний, не канонічний.** `_build_book_mapping()` виводить конкретне число для кожного модуля окремо на збірці (задокументований приклад у коді: KJV+ кладе Естер на позицію 190 замість стандартної). Ідентичність книги в сирому MyBible-файлі нестабільна між модулями — стабільна лише ПІСЛЯ нормалізації. Зберегти `book_number` як частину стабільного ключа розділу порушило б Інваріант 2 цього ж ADR у момент народження.
2. **Координати версифікаційно-відносні, не org-anchored.** Сирі `chapter_number_from/verse_number_from` мовчки припускають схему джерела (як і переклади — `russian_numbering` тощо). Зберігати їх напряму означало б рантайм-вгадування версифікаційної схеми коментаря — саме та рантайм-евристика, яку ADR-028 витер як клас. Нормалізація в org належить build-time.
3. **Немає provenance/статусу.** `marker/text` — усе, що дає MyBible-схема. Немає місця для `origin`/`translation_status`/`reviewer` — того, що потрібне для MT-циклу «випусти→вичитуй», який і є головним приводом цього ADR.

Побічна знахідка: `.commentaries.SQLite3`, який `build_db.py` вже парсить (`_read_commentaries_db`) — це НЕ повноцінні коментарі теологів, а виноски перекладу (`marker` типу `[1]` збігається з `<f>[1]</f>` у тексті вірша). Та сама MyBible-таблична схема, зовсім інше призначення.

**Рішення (підтверджено):** власна канонічна схема (org-anchored, стабільний хеш-ключ, provenance/status), як і рекомендовано в ADR. Імпортер MyBible-коментарів (крок 5 плану) перевикористовує вже написані `_open_mybible_sqlite`/`_detect_sqlite_schema`/`_build_book_mapping` з `build_db.py` — не пишеться наново. Один нюанс, якого не було в оригінальному тексті: діапазон MyBible-коментаря треба розгортати по-вірш і реверс-мапити КОЖЕН вірш через `verse_org`, а не лише індексувати старт+кінець (як зараз робить `index_range()` для міжглавних діапазонів вірш-індексу — прийнятне спрощення для пошукового індексу, недостатнє для якоря коментаря-модуля з чужою версифікацією; інакше похибка на межі глави класу ADR-028 D1/D3).

### §2 — FTS5 через ATTACH: варіант (a), перевірено емпірично

Спайк (ізольований, `python3 sqlite3`, SQLite 3.45.1 — не робоча база):

- ✅ FTS5-таблиця в attached БД працює напряму (`SELECT ... FROM calvin.comments_fts WHERE comments_fts MATCH ...`).
- ✅ **`UNION ALL` одним SQL-запитом** через кілька attached FTS5-таблиць, кожна з `JOIN` на власний `comments` того ж модуля, з єдиним `ORDER BY` на весь результат — працює.
- ⛔ FTS5 `content=` **обов'язково та сама БД**, що й сама FTS5-таблиця (спроба зовнішньої таблиці з іншої БД — тиха помилка `no such table` при `rebuild`). Це остаточно виключає варіант (b) чи будь-який гібрид «індекс у writable-шарі, контент у модулі»: SQLite фізично не підтримує таку конфігурацію, це не питання смаку.
- ⚠️ **`ATTACH` має ліміт** — зміряно 10 (`SQLITE_MAX_ATTACHED` за замовчуванням) на цій збірці SQLite. **Не підтверджено на iOS-збірці** — compile-time константа, платформо- і білд-залежна (GRDB може вендорити власну SQLite-амальгаму з іншими опціями компіляції). Перевірити на пристрої перед фіналізацією.

**Рішення (підтверджено): варіант (a).** Власна `comments_fts` на модуль (`content='comments'`, той самий токенайзер `unicode61 remove_diacritics 2`, що й `verse_fts`), будується на збірці модуля — нуль рантайм-індексації, оновлення книги вже несе оновлений FTS-фрагмент. Рантайм: динамічний `UNION ALL` по всіх attached модулях (перелік з `installed_modules`), **без BM25** — канонічне сортування `book_id (org), start_chapter, start_verse, source`, за тим самим принципом, який ADR-008 amendment 2026-08-07 вже прийняв для пошуку по віршах (однорідний корпус → BM25 не дає осмисленого порядку; тут іще й BM25 між різними FTS-індексами взаємно непорівнюваний — сильніший варіант того самого аргументу). Це працює лише тому, що Інваріант 1 (org-anchoring через `verse_org`) уже гарантує спільну систему координат для всіх модулів — самостійна вигода з першого інваріанта, не запланована окремо.

**Відкрито до підтвердження на пристрої:** факт ліміту `ATTACH`=10 на iOS-збірці SQLite; якщо каталог модулів колись наблизиться до стелі — або піднімати compile-time ліміт (якщо SQLite вендориться, не системна), або обмежувати «пошук по всіх модулях» релевантною підмножиною (активна книга/обрані джерела), а не безумовним fan-out. При старті (4 автори) — не блокер.

### §3 — Дельти всередині книги: відкласти підтверджено, тригер уточнено

Рішення ADR підтверджено, але розмитий тригер «якщо трафік стане проблемою» замінено на вимірюваний:

- Одиниця «книга» вже збігається з реальним темпом редагування — вичитка й доповнення коментарів природно йдуть по книгах/розділах (той самий каденс, що й волонтерська програма підрядника, `uk-interlinear-program.md`), не по одному вірші за раз. Sub-book дельта оптимізувала б вісь (розмір передачі), яку ще ніхто не зміряв як вузьке місце.
- Немає жодного виміряного розміру файлу «один автор × одна книга» — тільки сума (36 071 вірш-коментар на 4 джерела разом, `rebuild.sh`). Називати дельти потрібними чи непотрібними без цього числа — те саме «припущення замість виміру», від якого застерігає CLAUDE.md.

**Конкретний тригер (замість «якщо стане проблемою»):** зміряти найбільший реальний файл «автор × книга» під час Кроку 2 плану (Пілот на Кальвіні — уже заплановано). Якщо найбільший такий файл перевищує **~5–10 МБ** (типова межа, після якої мобільні OTA-оновлення прийнято ґейтити на Wi-Fi/попереджати користувача) — переглянути це рішення. Якщо ні — sub-book дельта лишається поза MVP свідомо, з датою й числом, а не за замовчуванням.

### §4 — Підпис модулів: checksum на MVP підтверджено; знайдено внутрішню суперечність

Модель загроз:

- **Підміна в дорозі** — вже закрита HTTPS/TLS; checksum тут другорядний (ловить биту/перервану закачку, не цілеспрямовану атаку).
- **Компрометація сховища/маніфесту** (доступ до S3/R2 чи ключів білду) — checksum **не захищає**: хто контролює сховище, контролює і файл, і його checksum у `manifest.json` узгоджено. Це єдина загроза, від якої справді захищає криптопідпис (приватний ключ поза сховищем).
- **Шкідливий контент модуля як SQL-поверхня** (побоювання, назване в самому ADR) — на iOS SQLite не завантажує розширення з файлу даних, тож виконання довільного коду через `.db`-файл нереалістичне. Реалістичний гірший випадок — DoS через биту схему/абсурдний вміст або підмінений текст, не RCE.

**Підтверджено на MVP:** зараз немає sideload/маркетплейс-потоку — усі модулі йдуть з власного курованого CDN, тобто межа довіри = та сама команда, що вже підписує сам застосунок для App Store. Це не нова категорія ризику, лише поширення наявної на текстовий контент. Криптопідпис вимагає інфраструктури ключів (де ключ, ротація, CI-секрет) — виправдано, коли з'являється sideload/маркетплейс, не раніше.

**Конкретний тригер (замість безрозмірного «fast-follow»):** будь-який план (a) сторонніх/sideload-модулів або (b) маркетплейсу без App-Review-еквівалентної курації. Рекомендований алгоритм на той момент: **Ed25519** — малий ключ, швидка перевірка, без PKI/X.509-ланцюга; публічний ключ вшитий у бінарник, приватний — офлайн/CI-секрет, підпис на SHA-256-диджест кожного файлу модуля, зберігається поряд у `manifest.json`.

**Знайдена суперечність у самій ADR (виправлено):** розділ «Жорсткі інваріанти дизайну» п.4 писав «checksum (SHA-256) + підпис» так, ніби обидва обов'язкові з MVP, тоді як «Відкриті питання» відкладали підпис на fast-follow. Текст п.4 вище вже узгоджено з цим рішенням.

**Незалежно від варіанту:** верифікація має фейлитись closed (відмова ATTACH-ити/встановити модуль при провалі checksum), а не open; atomic-swap-з-відкатом (уже в ADR) — достатній запобіжник навіть при MVP-рівні довіри.

## Amendment 2026-09-01 — мовний вимір схеми, фолбек між мовами, ліцензійна межа рос. джерел

Виявлено під час підготовки `plan-commentary-prerelease-fixes.md` до реалізації (розмова з
Іваном 2026-09-01, без коду) — при спробі полічити, які рос. джерела коментарів взагалі є в
`data/New/`, зʼясувалось, що §1 canonical-схема (Amendment 2026-08-28) спроєктована під
винятково англомовний корпус і не має виміру мови.

### Схема — колонка `language`, уточнений `translation_status`

- **`comments.language TEXT`** — нова колонка (`'en'` зараз, `'uk'`/`'ru'` у майбутньому).
  Ключ секції стає `hash(source|language|book|range)` — без мови `source='Calvin'`
  колізує між англійським і майбутнім українським Кальвіном: той самий твір, різний текст.
- **`translation_status` перевизначено, БЕЗ нового значення enum** (лишається
  `'source' | 'raw-mt' | 'reviewed' | 'final'`). Початкове припущення в цій сесії було
  додати пʼяте значення `'external'` для «готового чужого перекладу» — відхилено як зайве
  ускладнення: мова оригіналу твору взагалі не та вісь, яку це поле мало кодувати.
  Англійський Кальвін — теж переклад (з латини/французької, XIX ст.), так само як
  гіпотетичний ліцензований Генрі-рос — але жоден не потребує нашого MT-ревʼю.
  **`source` = будь-який готовий, стабільний текст, не вироблений нашим власним
  MT-конвеєром** — байдуже, оригінальна це мова твору чи чийсь готовий переклад.
  `raw-mt` → `reviewed` → `final` лишаються виключно для того, що виробляє **наш**
  пайплайн (перший кандидат — укр. Кальвін через скіл `calvin-ru-uk`).
- **`module_info` перескоповано на рівень мовного бандла, не одного твору** — наслідок
  фізичного розкрою нижче: замість метаданих одного автора (`author`, `version`) тепер
  `language`, `sources` (JSON-список творів у файлі з їхнім `origin`/датою імпорту),
  `book_versions` (як і було).

### Фізичний розкрій цього кроку плану — один файл НА МОВУ, не на твір

Рішення ADR (Amendment 2026-08-28 §1) — «одиниця доставки = твір, кожен окремий файл» —
залишається вірним для повного OTA-майбутнього (Кроки 3-4, ще не настали). Але для
`plan-commentary-prerelease-fixes.md` (без OTA, усе бандлиться) обрано проміжний варіант:
**один файл на мову** (`commentaries-en.db`, майбутній `commentaries-uk.db`) — не один файл
на весь корпус (простіше зараз, але довелось би пересплітати при переході на OTA) і не один
файл на кожного автора (OTA-готово вже зараз, але додає `ATTACH`/FTS5-`UNION`-складність,
для якої немає жодного use-case, поки книги ще не докачуються незалежно — саме та робота,
яку сам ADR explicitly відклав).

**Рантайм-наслідок — фолбек між мовами:** `commentaries-en.db` ATTACH-иться **завжди**,
незалежно від мови інтерфейсу (постійна підлога — доки не перекладено все, англійська
лишається обовʼязковою). Мовний оверлей (`commentaries-uk.db`) ATTACH-иться і йде першим
у пріоритеті, коли він є і має контент для конкретного `source`+org-діапазону:

```sql
SELECT * FROM (
    SELECT *, 0 AS prio FROM uk.comments WHERE source=? AND book_id=? AND <org verse in range>
    UNION ALL
    SELECT *, 1 AS prio FROM en.comments WHERE source=? AND book_id=? AND <org verse in range>
)
ORDER BY prio LIMIT 1
```

Це працює на рівні окремої секції (не цілої книги чи цілого автора) саме тому, що
org-якорення через `verse_org` (Інваріант 1) уже дає спільну систему координат для будь-якої
мови — той самий механізм, що й `UNION ALL`-пошук по кількох `ATTACH`-модулях з §2,
застосований до пріоритету мови замість пріоритету релевантності.

### Ліцензійна межа — рос. джерела `data/New/` заблоковані до окремої перевірки

Перевірено напряму (read-only, `mode=ro`) усі чотири рос. MyBible-модулі в `data/New/`:

| Джерело | `info.detailed_info` | Висновок |
|---|---|---|
| Генрі-рос (`Генри-к.commentaries.zip`) | «© 2002, 2007 Dutch Reformed Tract Society, Branch of the Netherlands Reformed Congregations, Netherlands. Russian edition» | **Явно захищений сучасний переклад, названий правовласник** — той самий клас проблеми, що NASB (P0, `legal/dataset-license-audit.md`), тільки тут одразу відомо, до кого звертатись |
| Августин-рос, Кальвін-рос, Сперджен-рос | без copyright-рядка в метаданих | Відсутність рядка **не є доказом PD** — перекладач/видавець невідомі з цих даних, потребують окремого дослідження |

**Рішення:** усі чотири лишаються поза бандлом до окремої перевірки прав (той самий підхід,
що вже спрацював для NASB і Огієнка — див. `legal/dataset-license-audit.md`). `data/New/*-к.zip`
і `АвгИпп.commentaries.zip` не видаляти, не імпортувати.

**Додатковий ризик, знайдений при цьому:** скіл `calvin-ru-uk` (переклад Кальвіна рос.→укр.)
бере джерелом саме `Кальвин-к.commentaries.SQLite3` — той самий файл із невідомим
провенансом. Якщо цей рос. текст виявиться не rights-clear, похідний укр. переклад
успадковує ту саму проблему незалежно від того, чи потрапить сам рос. текст у застосунок.
Не досліджено в цій сесії — окрема дія.

### Наступний крок

`plan-commentary-prerelease-fixes.md` оновлено відповідно (scope: v1 = лише
`commentaries-en.db`, рос. джерела виключені явно, не мовчки).

## Що переглянути з ростом

- Якщо трафік болить → sub-book дельти замість повної книги.
- Якщо потрібен маркетплейс сторонніх модулів → криптопідпис + curated-реєстр обов'язкові.
- Якщо перекладів багато мовами → `translation_status` розшириться в повноцінний перекладацький workflow (можливо, окремий інструмент вичитки поверх майстра). **Перший крок зроблено Amendment 2026-09-01** (`language`-колонка, EN↔UK фолбек через ATTACH+UNION); повноцінний workflow (окремий інструмент вичитки) лишається відкритим, коли перекладів стане кілька одночасно.
