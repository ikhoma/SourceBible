# Description

У NASB тап по слову, тегованому номером з діапазону **H9000+**, дає загальний порожній
стан «Language data unavailable for this word» — тобто лексикон не знайдено взагалі.
У KJV, ASV і RST те саме місце працює.

Ці номери не помилка модуля: діапазон H9000+ створений Tyndale House для NASB
(«Numbers beyond 9000 include non-lexical prefixes and suffixes» — шапка TBESH).
Застосунок має для них `NASBExtendedOverride` на 391 ключ. Але на тому шляху, яким
іде тап, ця мапа не застосовується.

## Steps to Reproduce

1. Перемкнутись на **NASB**, відкрити Лев 20:17.
2. Тапнути `it is a disgrace;` (у модулі це `<S>9155</S>`).
3. Вкладка **Слово** → **Значення**.

## Expected

Лексикон слова, як у KJV (там те саме місце тегується звичайним `2617`).

## Actual

«Language data unavailable for this word» (`WordTabView:37`, тобто `strongsEntry == nil`).

# Причина — два шари (заміряно 2026-08-19)

**1. У `strongs` НУЛЬ рядків діапазону H9xxx.** Тому будь-який `loadStrongs(id: "H9nnn")`
повертає `nil`. Це не діра в конкретному номері, а відсутність усього діапазону.

**2. Фолбек-шлях не застосовує override-мапу — і це головне.**
`tapWord(_ segment:in:)` спершу пробує Macula-слово (`:1065`), і для NASB воно НЕ
знаходиться: NASB тегує 9155, Macula тримає H2617a, вони не зіставляються. Тоді йде
фолбек `loadStrongs(for: segment)` (`:1067`), а той резолвить через `resolveStrongsId`,
який лише додає префікс `H`/`G`:

| функція | застосовує `nasbExtendedOverride`? |
|---|---|
| `resolvedMaculaBase` (мапінг слово↔сегмент) | **так** |
| `resolveStrongsId` (фолбек лексикону) | **ні** ← дефект |

Тобто мапа, створена рівно для цього випадку, на цьому шляху не викликається.

# Масштаб

| | |
|---|---|
| різних H9xxx номерів у тексті NASB | **603** |
| покриті `NASBExtendedOverride` | 391 |
| **НЕ покриті** | **212** (532 теги) |
| віршів NASB, що містять H9xxx теги | 3 794 |

Найчастіші непокриті: `H9411` (61), `H9111` (26), `H9583` (13), `H9330` (12), `H9478` (11).
`H9155` із репорту — не покритий, зустрічається 2 рази.

# Напрям (потребує рішення)

**Крок 1 — дешевий, окупає одразу.** Застосувати `nasbExtendedOverride` у фолбек-шляху
теж. Це поверне лексикон для **391 із 603** номерів без жодної зміни даних.
⚠️ Перевірити, що override віддає номер, для якого рядок у `strongs` справді існує —
інакше поміняємо один порожній стан на інший.

**Крок 2 — решта 212.** Це вже дані, не код: потрібне джерело відповідностей
H9xxx → Macula. Дотично до `strongs-mismatch-analysis.md` (рекомендація: Macula-anchored,
seeded from STEPBible dStrong/uStrong) і до ADR-016 Phase 2 (`verse_markup`).

**Крок 3 — чесний порожній стан.** Поки 212 не покриті, «Language data unavailable»
принаймні правдиве. Але варто відрізняти «слово не тегується цим перекладом» від
«лексикон не знайдено» — зараз обидва дають той самий рядок.

## КРОК 1 ЗАСТОСОВАНО 2026-08-19 — override на фолбек-шляху

**Змінено:** `ReaderViewModel.resolveStrongsId` — для номерів **≥ 9000** тепер
застосовується `nasbExtendedOverride`, як це вже робив `resolvedMaculaBase`.
Одна функція, один виклик у коді (`:1191`), тож зміна локальна.

Обмеження діапазоном навмисне: усі 391 ключ мапи справді ≥ 9000 (перевірено), а сліпе
застосування до звичайних номерів мовчки перемапило б справжні Strong's-id.

### Що це дає — заміряно по модулю NASB

| з 4 948 тегів H9xxx | |
|---|---|
| **отримують лексикон** | **3 795** (77%) |
| мапа є, ціль відсутня в `strongs` | 621 |
| мапи немає взагалі | 532 |

### Чому 621 НЕ «безнадійні» — і чому їх усе одно не чіпаємо

Мапа вказує на **голі** номери, а частина даних живе лише під суфіксами:

```
9238 → 3887      H3887  — рядка НЕМАЄ
                 H3887a — є («scoffer»), H3887b, H3887c — теж є
```

Те саме з `H2050` (найчастіша ціль серед відсутніх) і `H862`. Це той самий візерунок,
який CLAUDE.md фіксує для TBESH: для частини номерів bare-рядка не існує взагалі.

Тобто дані є, але щоб ними скористатись, треба вибрати між `a`, `b` і `c` — а це рівно
та задача зіставлення схем нумерації, яку bug-046 залишив невирішеною, і саме там
доведено, що суфікси можуть означати протилежне (hesed I проти hesed II).
⛔ Не вибирати навмання: помилка тут дає не порожнечу, а чуже значення.

**Регресії немає:** до фікса `S9238` давав `H9238` (рядка немає), після — `H3887`
(рядка немає). Результат той самий, але тепер він у правильному просторі номерів.

## КРОК 1 ВІДКОЧЕНО 2026-08-19 — мапа не лексиконна (заміряно)

Перевірка на пристрої показала, що фікс не працює на Лев 20:17 — `9155` немає в мапі.
Пошук придатного для перевірки вірша й виявив справжню проблему.

**Мапа віддає нісенітницю, якщо читати її як лексиконну.** Заміряно по всьому модулю
NASB — 2 555 місць, де ціль має визначення:

| | |
|---|---|
| визначення цілі перетинається з англійським словом біля тега | **384 (15%)** |
| **не перетинається** | **2 171 (85%)** |

Приклади не «майже правильні», а повністю чужі:

```
«villages»  → S9161 → H871  = Atharim   (місто)
«equipped»  → S9139 → H3641 = Calneh    (місто)
«Edom»      → S9000 → H1886 = Dothan    (місто)
«scribes»   → S9373 → H1886 = Dothan
```

### Чому цього ніхто не помічав

`nasbExtendedOverride` існує для **зіставлення слово↔сегмент** (`resolvedMaculaBase`),
а не для пошуку словникової статті. Там хибний номер просто ні з чим не збігається,
і слово лишається неклікабельним — м'яка, невидима відмова. Той самий хибний номер у
лексиконі дає **впевнене хибне значення**, тобто рівно те, що bug-046 сьогодні прибрав.

⛔ **Не відроджувати цей фікс.** Попередження записане просто в
`ReaderViewModel.resolveStrongsId`, поруч із кодом.

### Що це відкриває

Цілі, на які вказує мапа, — та сама родина «хибних базових рядків», що й у bug-046:
`H1886` (Dothan), `H871` (Atharim), `H3641` (Calneh). Той самий `H3641`, чий підзапис
`H3641b` показував «Calneh» для займенника הוּא на 2 651 вживанні. Тобто це не дві
різні проблеми, а одна: **базові рядки для частини номерів у `strongs` наповнені
чужими даними**, і будь-який шлях, що на них спирається, успадковує помилку.

### Стан

Порожній стан лишається — і це поки найчесніше, що можна показати. Потрібне справжнє
джерело відповідностей H9000+ → Macula (кандидат: STEPBible dStrong/uStrong, як радить
`strongs-mismatch-analysis.md`), а не переінтерпретація наявної мапи. Це робота з
даними рівня ADR, разом із bug-046 варіант B.
