# Description

In the Original tab, the transliteration under each Hebrew word came from a
**different verse**. The Hebrew text, Strong's numbers and glosses were correct;
only the transliteration line was wrong. Measured across the OT: **1,427 verses
(8.70% of those with data)**, 917 of them in Psalms.

The failure is silent and reads as precision — a reader sees a confident
transliteration that simply does not belong to the word above it. That is worse
than the English gloss it sits next to, which is at least true.

## Steps to Reproduce

1. Open Пс. 50:7 (Ukrainian numbering) — MT Psalm 51:7.
2. Bottom sheet → Word → Original.
3. Compare the transliteration line against the Hebrew.

## Expected

`הֵן` shows `hên`, `בְּעָווֹן` shows `bə-‘ā-wō-wn`, and so on.

## Actual

The six slots showed `tə-ḥaṭ-ṭə-’ê-nî`, `ḇə-’ê-zō-wḇ`, `wə-’eṭ-hār`,
`tə-ḵab-bə-sê-nî`, `ū-miš-še-leḡ`, `’al-bîn` — word for word the transliteration
of MT Psalm 51:9, two verses further on.

## Root cause

`fetch_biblehub_translit_hebrew.py:171` enumerates verse refs from the Macula
WLC TSV, which is **Masoretic** numbering, and pastes them straight into the URL:

```python
url = "https://biblehub.com/text/%s/%d-%d.htm" % (slug, ch, vs)
```

BibleHub serves **English** numbering at those URLs. Where a psalm carries a
superscription the English count starts after it, so `psalms/51-7.htm` returns
MT 51:9. The scraper then filed that page under the Masoretic key, and the
discrepancy became invisible.

**Why the existing guard missed it.** `_apply_bh_hebrew_translit()` had one
check: word-count parity. MT 51:7 has 6 display slots; English 51:7 also has 6
words. 6 = 6, so the guard passed and the corrupt data was written. A shifted
verse very often has the same word count, which makes count parity structurally
unable to detect this class.

**The check that would have caught it was designed but never implemented.**
ADR-020 specifies a level-2 per-slot Strong's comparison. It exists only in the
ADR text and in `validate_bsb_hebrew_translit.py`; `build_db.py` never got it.
H2005 vs H2398 on the first slot would have failed on day one.

**It had already been found once and lost.** The docstring of
`validate_bsb_hebrew_translit.py` (lines 51–56) states plainly that the scraper
fetches the wrong verse in shifted chapters. The note assumed the count guard
nulled most of it, nobody measured that assumption, and it was never raised as a
bug.

## Fix

Three new scripts, plus a decision to treat the ORG↔ENG relation as N:M rather
than 1:1.

**`scripts/derive_org_to_eng.py`** — derives the Masoretic→English map from data
instead of from `verse_map` (which ADR-028 measured as 57% wrong). Macula gives
the ORG stream, `bsb_tables.tsv` gives the ENG stream; both describe the same
text in the same order, so each ORG verse is located by Strong's content, never
by arithmetic. No offset table is hardcoded.

The unit is a **segment**, not a verse, because English folds a psalm's
superscription into verse 1 — MT 3:1 and MT 3:2 both live inside ENG 3:1 — and
occasionally splits a long MT verse across two ENG verses:

```
osis  org_ch  org_vs  seg  eng_ch  eng_vs  word_offset  word_len
PSA   3       1       0    3       1       0            6
PSA   3       2       0    3       1       6            5
PSA   3       3       0    3       2       0            8
```

**`scripts/fetch_biblehub_translit_hebrew_v2.py`** — fetches by English ref,
slices each page between the Masoretic verses that share it, and files the
result under the Masoretic key. Slicing happens at fetch time, so the JSON keeps
its existing contract and **`build_db.py` needed no change at all**. Boundaries
inside a shared page are recomputed from the live BibleHub page rather than from
BSB's word counts, because the two sources tokenise a handful of verses
differently. Every verse is validated against Macula's Strong's before it is
written.

**`scripts/fix_translit.sh`** — six gated stages: preflight and backup, baseline
audit, derive + self-check, plan, two fetch passes, final audit. Each stage stops
the run rather than carrying bad data forward.

## Result

| | before | after |
|---|---|---|
| corrupt verses | 1,427 (8.70%) | 0 |
| verses with no transliteration | 4,973 | 0 |
| anchors passing | 1/8 | 8/8 |
| MT Ps 51:7 agreement | 0.00 | 1.00 |

30 verses are stored as `marginal` (agreement 0.30–0.70). Spot-checked against
Macula: these are the right verses where the two sources assign different lexeme
ids to the same word — H582/H376 for "man", H7462/H7473 for "shepherd", H6030 vs
H6031 — or where BibleHub emits a word with no Strong's at all. Not corruption.

## Verification

`scripts/tests/test_translit_pipeline.py` — 18 tests, no network, no DB. One per
defect that actually shipped, named after the defect. Run:

```
python3 -m unittest discover scripts/tests
```

## Notes

The scale of this bug was set by an assumption nobody measured. Two independent
systems agreed on it in the end — the derived map flagged 1,508 verses as
shifted, the content audit flagged 1,427 as corrupt, and 1,404 were the same
verses — but that cross-check only happened because the map was built to be
checkable. See `CLAUDE.md` → «🔬 Дані перед висновком» and «🧪 Перевірки — у код,
не в очі» for the working rules this produced.
