# Description

In Word → Usage, some lines start with a leading space and some don't —
inconsistent indentation of the text.

## Steps to Reproduce

1. Switch translation to RST.
2. Open 2Цар 22:51 → Word → Usage.

## Expected

No leading space before the first letter on any line.

## Actual

Some entries start with a space, some without.

- Drive mailbox: `img/35.jpg`

Tester's own ref: "BUG REPORT 22". iPhone 11 / iOS 26.5.

## Investigation (2026-06-26 · subagent, sonnet)

**Real bug.** `highlightedVerseText()` (`WordTabContent.swift` ~461–524) assembles
segments via `strippingBibleMarkupKeepingSpaces()` (which intentionally preserves
leading spaces for mid-verse separation); the **first** segment keeps whatever leading
space the raw RST verse text has in the DB, and the final `AttributedString` is never
trimmed. RST raw rows inconsistently start with a space → some lines indented.
**bug-009 is the same root cause.**

## Proposed fix

Trim leading whitespace from the first segment (or the final result) in
`highlightedVerseText`; do NOT change the keep-spaces helper. Merge **bug-009 → bug-008**.
Confidence: high.

## Root cause (2026-07-13)

`highlightedVerseText` (WordTabContent.swift) builds each Usage snippet from
per-segment `stripKJVSegment()` → `strippingBibleMarkupKeepingSpaces()`, which
deliberately **preserves** leading spaces: the source encodes inter-word spacing as a
*leading* space on each segment, and trimming it makes words run together
("lodgedround aboutthe"). Correct between segments — but at the **edges of the verse**
that space leaks out as a stray indent. A verse whose first segment starts with a space
renders indented; one that doesn't renders flush. Hence the inconsistency.

## Fix

Trim the leading space on the first segment and the trailing space on the last, after
segmentation and before rendering. Inner spacing untouched. Build green; pending device QA.
