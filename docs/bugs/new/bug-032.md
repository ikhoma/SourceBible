# Description

Перше відкриття підвкладки **«Вживання»** для слова помітно «підлагує» — між тапом
і появою списку є пауза. Решта застосунку відчувається миттєвою, тому саме тут
затримка кидається в очі.

⚠️ **Формулювання навмисне обережне.** Репортер сам припускає, що абсолютна цифра
може бути невеликою (~50 ms) і проблема радше в **контрасті** з рештою UI, ніж у
довгій операції. Тому перший крок — **виміряти**, а не оптимізувати. Якщо замір
покаже 50 ms, це питання перцепції (див. §Якщо це перцепція), а не продуктивності.

## Steps to Reproduce

1. Відкрити будь-який вірш → Study Mode.
2. Тап по слову → вкладка «Слово».
3. Перемкнути підвкладку на «Вживання».
4. Спостерігати паузу перед появою списку. На частотному слові (יהוה, θεός)
   помітніше, ніж на рідкісному.

## Expected

Список зʼявляється так само миттєво, як решта переходів у панельці.

## Actual

Відчутна пауза. Повторне відкриття того самого слова — миттєве
(`usageLoaded` guard працює).

# Аналіз (структурний, БЕЗ заміру — 2026-08-02)

Три окремі причини, кожна реальна, але з дуже різною вагою. Порядок нижче — від
найбільш підозрілої до найменшої.

## A. N+1 запитів у `loadBookUsageGroups` — головний підозрюваний

`DatabaseService.loadBookUsageGroups` робить:

| | запит | скільки разів |
|---|---|---|
| A | `COUNT(*)` по `word` з GLOB-фільтром | 1 |
| B | `GROUP BY book_id` + `MIN(chapter*1000+verse)` | 1 |
| C | текст вірша-прикладу | **по одному на КОЖНУ книгу** |

Query C — у циклі `for row in bookRows`, і кожна ітерація це запит із **чотирма
`LEFT JOIN`** через `verse_org` / `verse` (версифікація, ADR-028). Для יהוה це
39 окремих round-trip'ів у SQLite; для θεός — 27.

**Гіпотеза:** саме цей цикл, а не обсяг даних, дає паузу.

**Виправлення:** схлопнути C у ОДИН запит для всіх книг одразу. Варіанти:
- window function (`ROW_NUMBER() OVER (PARTITION BY book_id ORDER BY chapter, verse)`)
  — SQLite 3.25+, доступна на всіх підтримуваних iOS;
- або `WHERE (book_id, chapter, verse) IN (…)` зі списком ключів із Query B —
  простіше, менш елегантно, але той самий ефект (1 round-trip замість N).

⛔ **Ризик середній.** Запит C несе логіку версифікації (ADR-028: псалмові
надписання, міжглавові зсуви) і fallback-переклад. Переписаний запит **мусить
давати побайтово той самий вихід**, інакше зламається відображення прикладів для
Псалмів. Верифікація нижче.

## B. Синхронний виклик на головному потоці

`loadUsageIfNeeded()` викликається з `.onAppear` і виконує весь блок A+B+C
**синхронно**. Тобто це не «повільно малюється» — це головний потік стоїть.

**Побічна знахідка:** у `ConcordanceView` **уже написаний спінер** для стану
`!entry.usageLoaded` — але його ніколи не видно, бо робота блокує той самий кадр,
у якому спінер мав би зʼявитись. Заготовка під асинхронність є, важіль не смикнуто.

**Свідомо НЕ беремо зараз.** Репортер: «спінер то таке». Асинхронність не робить
швидше — вона робить затримку *видимою*. Якщо A прибере затримку, спінер не
потрібен узагалі. Повертатись до B тільки якщо після A пауза лишиться.

## C. Нелінивий рендер

`ForEach(entry.bookGroups)` сидить у звичайному `VStack` (`PillSection`) всередині
нелінивого `ScrollView` → всі рядки будуються за один кадр. Кожен `BookUsageRow`
у `body` викликає `highlightedVerseText()`, яка парсить сиру KJV-розмітку
(`<S>H430</S>`) в `AttributedString`.

**Але стеля низька:** рядок = одна КНИГА, не одне входження. Максимум 66 рядків,
типово 20–40. `LazyVStack` тут дасть мало — це не список на 500 елементів
(поширене непорозуміння: 6512 — це кількість *входжень*, а не рядків).

Брати як дешевий причіп, не як окрему роботу.

# План: спершу замір, потім A

## Крок 1 — виміряти (обовʼязково перед будь-якою зміною)

Тимчасові `os_signpost` / `CFAbsoluteTimeGetCurrent()` навколо трьох ділянок
окремо, вивід у консоль:

1. Query A+B
2. цикл Query C (і **кількість ітерацій**)
3. побудова в'ю (перший кадр після `usageLoaded = true`)

Прогнати на **трьох словах різної частотності**: יהוה (6512 / 39 книг),
θεός (~1300 / 27 книг), рідкісне hapax (1 книга). Порівняння частотного з
рідкісним відразу скаже, чи винен цикл: якщо hapax миттєвий, а יהוה ні —
винен C, і A вирішує проблему.

⛔ Міряти **на пристрої**, не в симуляторі: симулятор має файловий кеш і диск
Mac'а, тож приховує саме те, що болить на реальному флеші.

⛔ Заміряти **на холодну**: після `usageLoaded` все безкоштовно, тож кожне
вимірювання — на новому слові або з перезапуском.

## Крок 2 — A, якщо замір підтвердив

Схлопнути Query C в один запит.

## Крок 3 — верифікація A (не «зібралось = ок»)

Порівняти вихід старої і нової реалізації **порядково** для набору слів:
- частотне OT (יהוה) — усі 39 книг;
- частотне NT (θεός);
- **слово з Псалмів** — перевірка надписань (ADR-028, найризикованіше місце);
- слово, де переклад не має тексту → має спрацювати fallback (`isFallback`);
- слово з sub-entry (H835a) — перевірка GLOB-стрипу суфікса.

Звірити для кожної книги: `bookId`, `count`, `chapter`, `verse`, перші 40 символів
тексту, прапорець `isFallback`. Розбіжність у будь-якому полі = стоп.

**Найзручніше** — не UI-тест, а разовий скрипт на Mac, що ганяє обидва SQL по
`sourcebible.db` і дифає результат. ⛔ Тільки читання, тільки на Mac
(sourcebible.db — APFS sparse, з пісочниці НЕ писати).

## Якщо це перцепція, а не мілісекунди

Сценарій, який репортер вважає ймовірним: цифра мала, але пауза є, і на тлі
миттєвої решти вона читається як лаг. Тоді допомагає не оптимізація, а
**прибирання порожнього кадру**:

- **префетч** — почати вантажити Usage у фоні, щойно відкрито вкладку «Слово»
  (тобто ще на підвкладці «Значення»), а не за фактом переходу на «Вживання».
  Користувач майже завжди спершу дивиться значення — цього часу вистачає.
  Найдешевший і найчесніший варіант: до моменту тапу дані вже є.
- **скелетон** замість спінера — рядки потрібної висоти сірими плашками, щоб
  висота списку не стрибала.

Префетч, імовірно, бʼє і A, і B за співвідношенням «ефект / ризик», бо взагалі
прибирає очікування з критичного шляху. Розглянути ПІСЛЯ заміру — якщо цифра
справді ~50 ms, починати треба з нього, а не з переписування SQL.
