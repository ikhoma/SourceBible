Design Principles

SourceBible is a scholarly Bible reader built for deep, unhurried engagement with sacred text. The design system is built on four principles: Legibility first — every typographic choice serves the reading experience; Respectful restraint — no decorative colour, UI steps back to let the Word speak; Adaptive fidelity — all tokens resolve to iOS semantic system colours so dark mode, accessibility text sizes, and high-contrast modes are handled by the OS; Source transparency — the original-language layer (Hebrew/Greek Macula) and the translation layer share the same visual weight, differentiated only by typeface.

Annotation Highlights

Four reader-annotation colours. All are rendered as semi-transparent overlays so the underlying verse text remains fully legible. Opacities are calibrated — yellow at 40%, green at 35%, blue at 28%, rose at 30% — because warm hues require more transparency to avoid washing out serif glyphs.

#FFCC00 × 40%
highlight.yellow
HighlightColor.yellow · systemYellow × 0.40
Default highlight colour. Conventional "marker" association makes it the most intuitive first pick. Suitable for general reading annotations and important phrases. Persisted as rawValue "yellow" in SQLite.
#34C759 × 35%
highlight.green
HighlightColor.green · systemGreen × 0.35
Promises, fulfilled prophecies, covenant language. A lighter opacity than yellow (35%) because green pigment renders darker at equal alpha. Stored as "green".
#1A6CF0 × 28%
highlight.blue
HighlightColor.blue · systemBlue × 0.28
Doctrinal statements, historical notes, cross-reference anchors. Lowest opacity (28%) because it shares the hue with the accent — too saturated and it competes with the selection state. Stored as "blue".
#FF2D55 × 30%
highlight.rose
HighlightColor.pink · systemPink × 0.30
Personal resonance, prayer verses, emotionally significant passages. The warmest colour in the set — use sparingly. Internally named "pink" for backward compatibility with stored rawValues. Stored as "pink".

Swift Implementation Notes

These tokens will live in a DesignSystem Swift file (or an Assets.xcassets Color Set catalog). Key rules:

Recommended token structure
// DesignSystem/Colors.swift
extension Color {
  // Brand
  static let dsAccent       = Color.accentColor
  static let dsAccentSubtle = Color.accentColor.opacity(0.06)
  static let dsAccentMuted  = Color.wordHighlight // exists

  // Backgrounds (use semantic names)
  static let dsCanvas    = Color(.systemGroupedBackground)
  static let dsSurface   = Color(.systemBackground)
  static let dsSurface2  = Color(.secondarySystemGroupedBackground)
  static let dsFill      = Color(.systemFill)
  static let dsFill2     = Color(.secondarySystemFill)
  static let dsFill3     = Color(.tertiarySystemFill)
}
Key constraints
  • Never hard-code #FFFFFF or #000000 for backgrounds — use semantic colours so dark mode works automatically
  • All text colours use .foregroundStyle(.primary/.secondary/.tertiary) — these adapt to contrast modes
  • Accent is set via Xcode project accent color (Assets.xcassets → AccentColor) — Color.accentColor automatically uses it
  • Annotation colours are persisted as String rawValues in SQLite via HighlightColor enum — never store UIColor/Color directly
  • iOS 26 CapsuleNavGroupStyle uses .glassEffect() — no background token needed; iOS ≤ 25 falls back to dsFill2
  • Typography: always use Dynamic Type text styles — no fixed sizes outside of SF Symbol size modifiers
