# Нова машина — від `git clone` до запущеного застосунку

**Status:** Draft (2026-08-08)

Цей документ відповідає на одне питання: **що потрібно на чистому Mac, окрім клону
репозиторію.** Заведений, бо `.gitignore` посилався на нього у двох місцях, а самого
файлу не існувало — шлях відтворення не був записаний ніде.

⛔ **Тут НЕ живе перелік датасетів і ліцензій** — це `docs/db_build.md`, і воно там одне.
Тут — тільки те, чого немає в git, і в якому порядку це роздобути.
⛔ **Тут НЕ живе процедура збірки бази** — це `./rebuild.sh`, виконуваний скрипт, який
не може розійтися з реальністю так, як розходяться документи.

---

## Що вже є в клоні

`CLAUDE.md` (тверді правила), увесь `docs/` (карта `INDEX.md`, 34 ADR, spec-и, PDR,
хронологія `LOG.md`, протокол пам'яті `WIKI.md`, баги й UX), `scripts/` разом із
лінтером пам'яті та збирачем LOG, Swift-код, `SourceBible.xcodeproj`, ассети обкладинок,
`Secrets.xcconfig` (шаблон, без значень) і `data/versification/` — чотири куровані
файли, яким у `.gitignore` зроблено явний виняток саме на цей випадок (ADR-028).

Агентові цього достатньо, щоб зрозуміти проєкт: він читає `CLAUDE.md`, далі `INDEX.md`,
і має більше контексту, ніж дає сам код. **Але зібрати застосунок із цього не можна.**

## Чого в git немає (заміряно 2026-08-08)

| Що | Розмір | Без нього |
|---|---|---|
| `sourcebible.db` + копія в `SourceBible/Resources/` | **340 MB** кожна | застосунок не запуститься — база бандлиться |
| `data/` (крім `versification/`) | **1.6 GB** | нема з чого перезібрати базу |
| `Config/Secrets.xcconfig` | 935 B | немає Mixpanel-токенів (шаблон у git є) |

Реальних токенів в історії git **немає** — трекається лише `Secrets.xcconfig` як шаблон
із порожніми значеннями. Перевірено 2026-08-08.

## Крок 1. Інструменти

- **Xcode** (+ Command Line Tools) і Apple ID для підпису.
  ⛔ CLion, VS Code та інші IDE тут не працюють: SwiftUI, `#Preview`, симулятор,
  Archive і TestFlight існують тільки в Xcode. Редагувати текст можна де завгодно,
  збирати — ні.
- **Python ≥ 3.10** з python.org. Системний `/usr/bin/python3` (Apple, 3.9.x)
  **не годиться**. Перевіряти вручну не треба: `rebuild.sh` робить це першим кроком
  і виходить із ненульовим кодом, друкуючи, який саме інтерпретатор підхопився.
- `pip3 install requests` — для завантаження крос-рефів з OpenBible.

## Крок 2. Секрети

Скопіювати `Secrets.xcconfig` → `Config/Secrets.xcconfig` і вписати три токени
(Dev / Beta / Prod — окремі проєкти Mixpanel, PDR-Analytics-Mixpanel D5). Інструкція
з підключення в Xcode — у шапці самого шаблону.

Файл гітігнориться. Токени беруться з вашого акаунта Mixpanel, не з репозиторію.

### ⛔ Якщо чіпаєш білд-фазу, що генерує `AnalyticsConfiguration.swift`

`SourceBible/Generated/AnalyticsConfiguration.swift` **не пишеться руками** — його генерує
Run Script фаза на кожній збірці, підставляючи токени з `Config/Secrets.xcconfig`. Правити
треба скрипт, а не згенерований файл (його перезапише наступний білд).

Пастка в тому, **де живе сам скрипт**: не окремим `.sh`, а рядком `shellScript = "…";`
всередині `project.pbxproj`. Через це текст проходить **два різні парсери підряд**:

1. парсер pbxproj — для нього це рядок у лапках, тож лапки всередині скрипта екрануються `\"`;
2. шелл — а він уже має бачити звичайні лапки.

Екранування, доречне на першому рівні, ламає другий. Реальний випадок: у heredoc
(`cat <<EOF > file`) стояло `\"${TOKEN}\"`. Усередині heredoc зворотний слеш — не
екранування, а звичайний символ, тож у згенерований Swift замість значення токена
поїхало сміття (`"token"` літералом).

**Чому це підступно: збірка при цьому ЗЕЛЕНА.** Файл згенеровано, Swift компілюється,
застосунок стартує — і мовчки шле аналітику з неправильним токеном. Ні помилки, ні
попередження; єдиний симптом — порожній дашборд через тиждень.

→ Правило: після будь-якої правки цієї фази **дивитись у згенерований файл**, а не на
результат збірки. Критерій: `mixpanelProdToken` непорожній і містить 32 hex-символи.
Те саме стосується `serverURL` (EU-хост, ADR-аналітика) — він теж підставляється звідси.

## Крок 3. База — два шляхи, і перший майже завжди правильний

### А. Перенести архівом зі старої машини ← за замовчуванням

`python3 scripts/pack_untracked.py` збирає все, чого немає в git, в один zip. Перелік
не хардкоджений: береться з `git ls-files --others --ignored`, тобто з самого
`.gitignore`, і розійтися з ним не може.

Три профілі (заміряно 2026-08-08):

| Профіль | Обсяг | Коли |
|---|---|---|
| `db` | **340 MB**, 2 файли | Працюєте над Swift-кодом. База + секрети, датасети не потрібні |
| `essential` (типово) | **1.1 GB**, 2 553 файли | Плюс датасети без кешів і локальних знімків |
| `full` | **1.9 GB**, 33 729 файлів | Плюс 624 MB кешу HTTP-скрейпу BibleHub, який качається заново |

Без `--write` друкує лише план: що береться, що пропущено і **з якою причиною** —
мовчазне викидання даних гірше за зайвий гігабайт.

В архів кладеться `MANIFEST.json` (sha256 бази, коміт-джерело, профіль), `RESTORE.md`
і виконуваний `restore.sh`, який на новій машині копіює файли, дублює базу в
`SourceBible/Resources/` і звіряє контрольну суму. Запускати **з кореня клону**.

⚠️ Архів містить `Config/Secrets.xcconfig` із живими токенами Mixpanel. Переносити
диском або зашифрованим каналом, у публічну хмару не класти, після розпакування
видалити. Скрипт друкує це попередження сам.

⚠️ Звірте коміт: якщо клон **старіший** за той, на якому зібрано архів, спершу
`git pull` — інакше база може не відповідати схемі в коді. `MANIFEST.json` містить
потрібний хеш, `RESTORE.md` нагадує про це.

Після відновлення в Xcode обов'язково **Clean Build Folder (⇧⌘K)** — Xcode кешує стару
базу, і без Clean код побачить стару схему.

Ручна альтернатива, якщо архів не потрібен: просто скопіювати `sourcebible.db`
(340 MB) в обидва місця — корінь репо і `SourceBible/Resources/`.

⚠️ Копіювати як звичайний файл. Якщо після копіювання Python читає базу з
`SQLITE_CORRUPT` (error 11) — це не пошкодження, а APFS sparse-файл; звірити `ls -ls`
(фізичні блоки проти логічного розміру). Деталі — `CLAUDE.md`, розділ «База даних».

### Б. Перезібрати з нуля

Потрібно **тільки** якщо ви змінюєте сам конвеєр збірки. Для роботи над Swift-кодом
не потрібно взагалі.

1. Роздобути датасети за таблицею в `docs/db_build.md` (посилання й ліцензії — там).
   ⚠️ NASB — ліцензований, не розповсюджувати. Owen — не включати в комерційні пакети.
2. Покласти у `data/`.
3. `./rebuild.sh` — ~15 хвилин на всі кроки.

Контрольні числа після збірки: `verse_org` = **155 621 рядок**, коментарі = **36 071
вірш**, база ≈ 340 MB. Суттєво менше — щось пішло не так.

## Крок 4. Перевірити, що машина здорова

```
python3 scripts/lint_docs.py
python3 -m unittest discover scripts/tests
```

Перше має дати «✓ Розходжень немає», друге — OK. Обидва виходять з нулем і не
потребують ані мережі, ані бази. Якщо лінтер падає одразу після клону — це справжнє
розходження в пам'яті проєкту, а не проблема машини.

Далі Xcode: ⇧⌘K → ⌘B → ⌘R на симуляторі.

## Робота на двох машинах

У git їде **пам'ять** — рішення, правила, хронологія. Не їдуть **артефакти** — база
й датасети. Тому обмін між машинами виглядає так:

- **Код і рішення** — через `git push` / `git pull`. Сюди ж усе, що ви ухвалили:
  трейлер `Decision:` у коміті переживе переїзд, згадка в чаті — ні.
- **База** — копіюванням, за потреби. Вона детермінована: та сама база з тих самих
  датасетів, тож синхронізувати щоразу не треба — лише коли конвеєр змінився.
- **`data/`** — тримати на одній машині, тій, де ви перезбираєте базу. Дублювати
  1.6 GB на обидві немає сенсу.

⚠️ Найдорожча помилка при переїзді — забути запушити. Незакомічена робота не існує
ніде, крім однієї машини: 2026-08-08 у робочій теці лежало 62 незакомічені файли,
включно з усією денною роботою над пам'яттю проєкту, і в origin їх не було.
